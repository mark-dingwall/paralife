## Summary

Phase 20.1 is a design-recovery phase. Phase 12 designed a sensory-organ model (D-19/D-20/D-21) where only SENSOR members produce composite vision via a stitched union. Phase 15's protocol overhaul (15-SCHEMA §11 / D-24/D-50 reversal table) dropped this and replaced it with flat authority tiers: LOCOMOTOR gets a 5x5 window centred on its own cell (same as a solo Particle), and SENSOR/DEFENDER get a minimal passive form. The stitched-union promise in §11 was listed but never built.

This phase restores the sensory-organ model: SENSORs are eyes; LOCOMOTOR/FEEDER/ATTACKER feel only their immediate adjacency; SENSOR/DEFENDER/REPRODUCER are passive. The key structural changes are: (1) TickBroadcaster gains a new per-role frame-building path that replaces the current `tierOf()` switch; (2) a per-tick SENSOR union projection is built from `CompositeRegistry.CompositeState`, feeding the LOCOMOTOR's `s` block; (3) `resolveReproducerBud` in ActionResolver drops its `directionOf(action)` dependency and gains a server-side nearest-free-cell scan; (4) HeuristicBrain's LOCOMOTOR path gets a real food/threat steering heuristic instead of a random shuffle; (5) `GoldenTraceEquivalenceTest` and `golden-trace-phase19.json` are re-baselined.

No wire protocol changes are needed. `MAX_S_ENTRIES`=256 and relative-coord +-63 are comfortably sufficient. `TickFrame.sensorRadius` continues to encode the LOCOMOTOR's window radius — the value will be `1` (8-cell adjacency = radius 1) plus the union cells appended to the same `s` block. This is a semantic change in what populates the `s` block, not a structural frame change.

**Primary recommendation:** Implement the `buildTickFrame` changes in TickBroadcaster first (per-role routing + SENSOR union construction), re-baseline the golden trace, then update HeuristicBrain. These are independent enough for sequential plans within one phase, but the golden trace re-baseline must be the last step.

## Research Q&A — Specific Questions Answered from Code

### Q1: Does SENSOR_PLUS_1 buff widen a SENSOR's contribution to the union, or only a solo entity's own vision?

**Answer: Solo entity's own vision only. It does NOT affect SENSOR member contributions to the union.**

Evidence: `TickBroadcaster.sensorRadiusFor()` (lines 434-445) checks `buffRegistry.hasBuff(botEntityId, BuffRegistry.BuffType.SENSOR_PLUS_1)` and yields `3` instead of `PERCEPTION_RADIUS` when the buff is active. This path is reached only for `AuthorityTier.FULL` and `AuthorityTier.AUTHORITY_LITE` entities. SENSOR members currently take `AuthorityTier.PASSIVE` and return `sensorRadius=0` before `sensorRadiusFor` is ever called. [VERIFIED: source code `TickBroadcaster.java` lines 422-445]

The buff comment in `BuffRegistry.java` (line 43) reads "vision 5x5 → 7x7" — it is described as expanding the entity's own vision radius, not its contribution to a composite union.

**Consequence for D-03:** In Phase 20.1, the SENSOR union construction will iterate SENSOR members' positions from `CompositeRegistry` and call `buildCellEntries(sensorPos, radius=2)` for each. Whether a SENSOR member holds `SENSOR_PLUS_1` is a separate question — the current design (D-03) fixes the contribution radius at 5x5 (radius-2). If the planner wants to honour `SENSOR_PLUS_1` for a SENSOR's contribution radius (radius-3 / 7x7), that is an extension beyond D-03 and should be a Claude's Discretion item or explicitly deferred. Given D-03 is locked at 5x5, the buff does NOT widen SENSOR contributions to the union.

**Planner action:** Union construction iterates all SENSOR members in the composite via `CompositeState.getMemberIds()`, checks `CompositeMember.role() == Role.SENSOR`, and calls `buildCellEntries(sensorPos, 2)` for each. No buff check needed. [ASSUMED: whether buff should optionally widen union contribution is unresolved by the user; D-03 says 5x5, so use 2.]

### Q2: TickBroadcaster seam — how does the D-01 per-role organ model replace `tierOf()`?

**Current code (VERIFIED: source):**

`buildTickFrame()` at line 353 calls `tierOf(occupant, bot.entityId())` which returns `AuthorityTier.FULL / AUTHORITY_LITE / PASSIVE`. Then `sensorRadiusFor(tier, bot.entityId())` maps FULL→2 (or 3 with buff), AUTHORITY_LITE→1, PASSIVE→0. A single `buildCellEntries(pos, radius)` call builds the entire `s` block.

**D-01 change:**

The new model breaks the single-radius path. Instead, `buildTickFrame` branches on role:

```
CompositeMember.role():
  LOCOMOTOR   → sensorRadius=1, cells = merge(buildCellEntries(pos,1), buildSensorUnion(compositeId, pos))
  FEEDER      → sensorRadius=1, cells = buildCellEntries(pos, 1)
  ATTACKER    → sensorRadius=1, cells = buildCellEntries(pos, 1)
  REPRODUCER  → passive (minimal form, sensorRadius=0)
  DEFENDER    → passive (minimal form, sensorRadius=0)
  SENSOR      → passive (minimal form, sensorRadius=0)
Solo / BondedPair → unchanged (sensorRadius=2 or 3 with buff)
```

`tierOf()` can be replaced or extended. The simplest refactor: rename/supersede `tierOf()` with a new `roleModelFor(Entity)` method that returns a richer enum or value object distinguishing LOCOMOTOR from other composite roles. The key seam is the single conditional at `buildTickFrame` line ~375 that currently dispatches on `tier == AuthorityTier.PASSIVE`. After D-01, the dispatch must distinguish LOCOMOTOR from FEEDER/ATTACKER from REPRODUCER/DEFENDER/SENSOR.

**OVERCROWDED omission (D-04):**

The D-40 expression in `envStateFor()` (line 696-701) currently runs for all entities:
```java
byte cellStatus = (byte) ((cached & ~BIT_OVERCROWDED) | perBotOvercrowdedBit);
```
For composite members (D-04), OVERCROWDED must always be 0. The change: add a branch in `envStateFor()` (or in its caller inside `buildCellEntries` / the new union builder) that passes `perBotOvercrowdedBit = 0` for composite member bots. The `cached & ~BIT_OVERCROWDED` strip already zeros bit 0 from the cache; the only remaining source of `BIT_OVERCROWDED` on the wire is `perBotOvercrowdedBit`. Zeroing that for composite frames makes D-04 a 1-line change at the call site in `envStateFor` or its callers.

Concretely: `buildCellEntries` accepts a `botPos` and `radius` but not a "bot is composite" flag. The cleanest approach is to pass an additional boolean `isCompositeMember` into `buildCellEntries` (or into a new overload called only for composite paths) and pass it down to `envStateFor`. Alternatively, since `buildCellEntries` is called from `buildTickFrame` where the occupant is known, the caller can compute a flag before the call.

**Important:** `VisionScopedOvercrowdingTest` currently pins the D-40 expression. That test must still pass for non-composite entities. The composite branch is additive, not a replacement.

### Q3: SENSOR union construction — where in the tick pipeline, and what APIs are available?

**Placement:** Inside `buildTickFrame`, called from `TickBroadcaster.onTick()` at `@Order(50)`. The D-41 status caches are rebuilt by `EnvironmentEngine` at `@Order(14)` — by the time TickBroadcaster runs, `getCellStatus()` and `getEntityStatus()` are current. The SENSOR union is a derived per-tick read-only projection of the same shape. It should be built inline in `buildTickFrame` for the LOCOMOTOR case, not cached globally (same pattern as D-41 status caches). [VERIFIED: source code]

**CompositeRegistry APIs (VERIFIED: source):**

```java
// Get all member IDs for a composite:
compositeRegistry.getComposite(compositeId)          // Optional<CompositeState>
compositeState.getMemberIds()                        // List<String> (unmodifiable view)
compositeState.getPositionForMember(memberId)        // Position (or null)
```

`getMemberIds()` returns a `Collections.unmodifiableList` view of a `CopyOnWriteArrayList`, so iteration is safe from the TickBroadcaster thread without locks.

**SENSOR enumeration algorithm (to implement in buildTickFrame for LOCOMOTOR):**

```java
// Called when occupant is CompositeMember with role == LOCOMOTOR
Optional<CompositeRegistry.CompositeState> stateOpt = compositeRegistry.getComposite(cm.compositeId());
if (stateOpt.isEmpty()) { /* fallback to radius-1 only */ }
CompositeRegistry.CompositeState state = stateOpt.get();

// Build union: LinkedHashMap<(dx,dy), CellData> keyed by relative position from LOCOMOTOR
Map<String, CellData> unionByRelPos = new LinkedHashMap<>();

// First: own 8-cell adjacency (radius=1, from LOCOMOTOR's position)
// ... buildCellEntries(pos, 1) — already produces CellEntry list

// Then: SENSOR contributions (radius=2, from each SENSOR's position)
for (String memberId : state.getMemberIds()) {
    Position sensorPos = state.getPositionForMember(memberId);
    if (sensorPos == null) continue;
    Cell sensorCell = worldGrid.getCell(sensorPos.x(), sensorPos.y());
    if (!(sensorCell.occupant() instanceof CompositeMember sc)) continue;
    if (sc.role() != Role.SENSOR) continue;
    // Build 5x5 window from sensorPos, express all coords relative to LOCOMOTOR pos
    // Deduplicate by (dx, dy) relative to LOCOMOTOR — first occurrence wins
    buildSensorContribution(sensorPos, locoPos, unionByRelPos);
}
```

**Deterministic ordering:** The union must be sorted before encoding to keep the golden trace stable. Sort by: (1) dy ascending, (2) dx ascending — matches the existing row-major emission order in `buildCellEntries` and is consistent with the "toroidal-normalized (y, x)" suggestion in Claude's Discretion. [ASSUMED: exact comparator; planner must pin this in the plan and the golden trace will lock it]

**±63 relative-coord constraint:** CompositeMembers are mutually adjacent on the torus (they move as a rigid body). The maximum composite diameter is bounded by the grid size, but in practice members cluster near each other. The ±63 relative range (from LOCOMOTOR's position) will not be exceeded for realistic composites. However, the plan should include a clamp + warn log (as `buildRosterIfChanged` already does at line 877) to match the existing pattern. `PerceptionCodec.encodeRelative()` already clamps silently via `clampRelative()` — the warn is the only addition needed.

### Q4: REPRODUCER auto-place (D-02) — current signature and required changes

**Current `resolveReproducerBud` (ActionResolver ~lines 847-890, VERIFIED: source):**

```java
private void resolveReproducerBud(ResolvedCompositeAction rca,
                                   CompositeRegistry.CompositeState composite,
                                   Set<Position> claimedCells) {
    // energy gate (unchanged)
    Direction dir = directionOf(rca.action);  // <-- reads bot-chosen direction
    if (dir == null) return;                   // <-- returns if no direction
    Position target = dir.apply(rca.bot.position(), ...);
    if (claimedCells.contains(target)) return;
    Cell targetCell = worldGrid.getCell(target.x(), target.y());
    if (targetCell.hasOccupant()) return;
    // spawn child, update eligibleCellIndex, liveEntityRegistry
}
```

**Required changes:**

1. Remove `Direction dir = directionOf(rca.action)` and `if (dir == null) return`.
2. Replace the single `target` computation with a nearest-free-cell outward scan from `rca.bot.position()`.
3. The scan must be bounded (D-02: "a bounded search radius so it never scans the whole grid"). Planner decides the bound — a reasonable default is `maxSearchRadius = 5` (covers REPRODUCER sheltered behind DEFENDERs in an ~10-cell colony diameter).
4. Tie-break: lowest wrapped-dy first, then lowest wrapped-dx (per D-02 prose recommendation). This is the same toroidal-normalized sort used in the union ordering.
5. If no free cell exists within the bound, skip (no error, no bud).

**Determinism concern for golden trace:** The scan order must be deterministic. A simple approach: generate all candidate positions within the search radius, sort by (wrappedDy, wrappedDx), iterate in that order picking the first that is free and not in `claimedCells`. No RNG involved — fully deterministic and stable across runs.

**Existing infrastructure:** The `claimedCells` set is already passed in and checked. `worldGrid.getCell(x, y).hasOccupant()` is the free-cell predicate. `Math.floorMod` for toroidal wrapping is used throughout the codebase. `eligibleCellIndex.notifyChanged()` is already called at the spawn site (line 875) and must remain.

**Note on `R` verb from the bot action contract:** The REPRODUCER's bot currently sends `a|R|<numpad>` (action verb R with a direction arg). With D-02, the direction arg becomes ignored server-side. The action contract (what verb the REPRODUCER bot sends) can remain `a|R|<anything>` — the server simply ignores the arg — OR the bot can send `a|R` (no arg, verb only). The `PerceptionCodec` parser at line 829 currently requires `R` to have a "single numpad digit" arg. Changing the bot to omit the arg would break the codec constraint. **Recommendation:** keep the bot sending `a|R|<numpad>` for now; server ignores the arg. A later phase can clean up the contract. This avoids a codec/protocol change in Phase 20.1.

### Q5: Golden-trace re-baseline — exact mechanism

**Current mechanism (VERIFIED: source, `GoldenTraceEquivalenceTest.java`):**

1. `driveScenario()` seeds 2 adjacent predator+prey pairs (forces bond formation via `bonding-probability=1.0`), then places 26 more bots via `handler.attemptPlacementForTest()`.

**Re-baseline procedure:**

1. Delete `src/test/resources/golden-trace-phase19.json`.
2. Run `GoldenTraceEquivalenceTest`. The test will fail with "BASELINE_PINNED" and write the new baseline.
3. Re-run the test. It should now pass.
4. Commit the new `golden-trace-phase19.json`.

**Which existing scenarios shift:** All scenarios that involve composite members with LOCOMOTOR or FEEDER/ATTACKER/REPRODUCER roles will shift because:

- FEEDER/ATTACKER change from radius-1 (3x3, 9 cells) to radius-1 (8-cell adjacency, same 3x3 window minus self = same cells — no change in cell count, but OVERCROWDED bit is now always 0).
- REPRODUCER goes from AUTHORITY_LITE (sensorRadius=1, has s block) to PASSIVE (minimal form, no s block) — **this is a significant frame shape change**.

Actually: REPRODUCER currently maps to `AuthorityTier.AUTHORITY_LITE` (line 427). Under D-01, REPRODUCER becomes PASSIVE (no vision block). This changes the frame shape for any session where the registered bot is a REPRODUCER. The existing golden trace almost certainly has composite-bearing sessions where members have REPRODUCER roles (the scenario forces composite formation via BondedPair bonding, and composite formation assigns roles). This will cause all REPRODUCER sessions to shift from a full-shape frame to a minimal frame.

**New SENSOR scenario:** The plan should add a `seedCompositewithSensorAndLocomotor()` helper (on the pattern of `seedAdjacentBondingPair`) that places a formed composite directly on the grid: a LOCOMOTOR + >=1 SENSOR members, all as `CompositeMember` entities registered with `compositeRegistry`. **`clearStateForTest()` / `resetAll()` contract:** The test already calls `actionResolver.clearStateForTest()` and `tickBroadcaster.clearStateForTest()` to prevent inter-run state leaks. If Phase 20.1 adds any per-tick derived state caches in TickBroadcaster (e.g. a cached union map), those must be cleared in `clearStateForTest()`.

### Q7: Wire/codec budget — MAX_S_ENTRIES and +-63 relative-coord for union

**MAX_S_ENTRIES = 256 (VERIFIED: `PerceptionCodec.java` line 29)**

Worst case union: 3 SENSORs each contributing a 5x5 window (25 cells each). Even with zero overlap that is 75 cells. Plus 8 cells from the LOCOMOTOR's own adjacency = 83 cells. 83 << 256. Well within budget even with env supplements (env-only cells that do not dedup but have env state). [VERIFIED: source]

**Relative-coord constraint +-63 (VERIFIED: `PerceptionCodec.java` line 290, `clampRelative`):**

The codec already clamps silently. Union cells from SENSOR windows are expressed relative to the LOCOMOTOR's position. Given that CompositeMembers form rigid bodies and move as a unit, the maximum separation between a SENSOR and a LOCOMOTOR is bounded by the composite's diameter. Current composites on a 16x16 test grid will never approach +-63. On a large production grid (e.g. 256x256), a very long composite could theoretically exceed +-63, but this is not a practical concern for Phase 20.1. The plan should add an assertion (not just silent clamping) in the union builder to log a warning if any cell would be clamped, matching the pattern in `buildRosterIfChanged` (line 877). [VERIFIED: source]

**sensorRadius field on TickFrame:** With D-01, LOCOMOTOR receives radius-1 own adjacency plus union cells in the same `s` block. The `sensorRadius` field on `TickFrame` is validated as 0..3 (line 88). For LOCOMOTOR under D-01, `sensorRadius` should be set to `1` (the 8-cell adjacency radius). The union cells appear in the `cells` list but they are not bounded by `sensorRadius` — the codec does not enforce that cell entries are within `sensorRadius` cells of the self position. `sensorRadius` is a wire signal to the client about the "primary" vision window; additional union cells simply extend the `s` block beyond what `sensorRadius` alone would suggest. The client (`HeuristicBrain`) reads `frame.cells()` directly and does not use `sensorRadius` to bound its scan. This is consistent with the existing design. [VERIFIED: source]

## Common Pitfalls

### Pitfall 1: LOCOMOTOR sensorRadius field confusion

**What goes wrong:** Planner sets `sensorRadius=2` for LOCOMOTOR to "match the old full-authority behaviour" — this sends a 5x5 window centred on the LOCOMOTOR's position, ignoring the organ model.

**Why it happens:** `sensorRadius` in `TickFrame` currently IS the vision window radius. Under D-01, the LOCOMOTOR's "primary" window is radius-1 (8-cell adjacency), with extra union cells appended to the same `s` block.

**How to avoid:** Explicitly set `sensorRadius=1` for LOCOMOTOR frames and build the `s` block as `buildCellEntries(pos, 1)` plus the SENSOR union. The `TickFrame` constructor does not validate that `cells` entries are within `sensorRadius` of self — it is just a signal field.

**Warning signs:** `CompositePerceptionTest.locomotorReceivesPoolAndEnergy` currently asserts `sensorRadius == PERCEPTION_RADIUS` (which is 2). This test MUST be updated as part of the plan. Leaving it as-is would force `sensorRadius=2`, contradicting D-01.

### Pitfall 2: Golden trace shifts more than expected

**What goes wrong:** REPRODUCER changes from AUTHORITY_LITE (sensorRadius=1, full frame) to PASSIVE (minimal form). This is a significant change for any session where the bot is playing a REPRODUCER role. The existing golden trace with `bonding-probability=1.0` will likely produce composites with REPRODUCER members.

**Why it happens:** D-01 marks REPRODUCER as passive, but the existing test comment says "REVIEWS CONSENSUS-H2 — scenario must trigger >= 1 bond OR composite formation" — composites will form, and composites get role assignments including REPRODUCER.

**How to avoid:** When re-baselining, delete the json file, run once to write the new baseline, re-run to confirm dual-run equivalence. The plan should include a step that explicitly verifies the dual-run equivalence before accepting the new baseline.

### Pitfall 3: Union cell coordinates expressed relative to wrong origin

**What goes wrong:** Union cells from a SENSOR's 5x5 window are expressed relative to the SENSOR's position rather than the LOCOMOTOR's position. The LOCOMOTOR bot cannot use them for navigation because it cannot resolve the coordinates to directions from its own cell.

**Why it happens:** `buildCellEntries(sensorPos, 2)` produces cells with `dx/dy` relative to `sensorPos`. These must be re-expressed relative to `locoPos` before merging into the LOCOMOTOR's `s` block.

**How to avoid:** The union builder must compute `unionDx = sensorDx + (sensorPos.x() - locoPos.x())` (wrapped) and `unionDy = sensorDy + (sensorPos.y() - locoPos.y())` (wrapped) for each cell from the SENSOR window.

### Pitfall 4: REPRODUCER action verb R codec constraint

**What goes wrong:** Removing the direction arg from REPRODUCER bot actions breaks `PerceptionCodec.validateActionArg()` which requires verb `R` to have a single numpad digit arg.

**Why it happens:** The codec enforces the wire grammar strictly. `resolveReproducerBud` does not need the direction anymore, but the bot still sends it.

**How to avoid:** Keep the bot sending `a|R|<any numpad>` for now; the server ignores the direction. Only the server-side `resolveReproducerBud` changes. A later phase can clean up the contract. Document this explicitly in the plan.

### Pitfall 5: Inter-run state leak in new TickBroadcaster state

**What goes wrong:** If `buildSensorUnion` caches anything per-composite or per-session, it will survive between `resetAll()` calls in `GoldenTraceEquivalenceTest` and cause digest divergence.

**Why it happens:** The test's `resetAll()` explicitly calls `tickBroadcaster.clearStateForTest()`. Any new per-composite cache in TickBroadcaster must be cleared there too.

**How to avoid:** Prefer pure stateless union construction (same as D-41 status caches: compute inline each tick, no persistent state). If caching is needed for performance, add a `clearStateForTest()` extension in TickBroadcaster.

```java
// Called when occupant is CompositeMember with role == LOCOMOTOR
private List<CellEntry> buildLocomotorCells(Position locoPos, String compositeId) {
    // 1. Own 8-cell adjacency (radius=1)
    List<CellEntry> adjacency = buildCellEntries(locoPos, 1);

    // 2. SENSOR contributions
    var stateOpt = compositeRegistry.getComposite(compositeId);
    if (stateOpt.isEmpty()) return adjacency;
    var state = stateOpt.get();

    // Key: relative (dx,dy) from locoPos — use LinkedHashMap to preserve insertion order
    // before sort. CellData from adjacency gets priority (first-in-wins on dedup).
    Map<Long, CellEntry> byRelCoord = new LinkedHashMap<>();
    for (CellEntry e : adjacency) {
        byRelCoord.put(relKey(e.coord()), e);
    }

    for (String memberId : state.getMemberIds()) {
        Position sensorPos = state.getPositionForMember(memberId);
        if (sensorPos == null) continue;
        Cell sc = worldGrid.getCell(sensorPos.x(), sensorPos.y());
        if (!(sc.occupant() instanceof CompositeMember cm2)) continue;
        if (cm2.role() != Role.SENSOR) continue;

        // Build 5x5 from sensorPos, re-express relative to locoPos
        List<CellEntry> sensorWindow = buildCellEntries(sensorPos, PERCEPTION_RADIUS);
        for (CellEntry entry : sensorWindow) {
            // Re-express coord relative to locoPos: add (sensorPos - locoPos) offset
            CellEntry reExpressed = reExpressRelativeToLoco(entry, sensorPos, locoPos);
            long key = relKey(reExpressed.coord());
            byRelCoord.putIfAbsent(key, reExpressed);  // adjacency wins on overlap
        }
    }

    // Sort by (wrappedDy, wrappedDx) for deterministic emission
    return byRelCoord.values().stream()
            .sorted(Comparator.comparingInt(e -> wrappedDy(e.coord()))
                    .thenComparingInt(e -> wrappedDx(e.coord())))
            .collect(Collectors.toList());
}
```

```java
private static final int MAX_REPRODUCER_SEARCH_RADIUS = 5;

private Position nearestFreeCell(Position origin, Set<Position> claimedCells, int maxRadius) {
    int w = worldGrid.getWidth(), h = worldGrid.getHeight();
    // Generate candidates sorted by (euclidean^2, wrappedDy, wrappedDx) for tie-break
    List<int[]> candidates = new ArrayList<>();
    for (int dy = -maxRadius; dy <= maxRadius; dy++) {
        for (int dx = -maxRadius; dx <= maxRadius; dx++) {
            if (dx == 0 && dy == 0) continue;
            candidates.add(new int[]{dx, dy, dx*dx + dy*dy});
        }
    }
    candidates.sort(Comparator.comparingInt((int[] c) -> c[2])
            .thenComparingInt(c -> c[1])
            .thenComparingInt(c -> c[0]));
    for (int[] c : candidates) {
        int tx = Math.floorMod(origin.x() + c[0], w);
        int ty = Math.floorMod(origin.y() + c[1], h);
        Position t = new Position(tx, ty);
        if (!claimedCells.contains(t) && !worldGrid.getCell(tx, ty).hasOccupant()) {
            return t;
        }
    }
    return null;
}
```
