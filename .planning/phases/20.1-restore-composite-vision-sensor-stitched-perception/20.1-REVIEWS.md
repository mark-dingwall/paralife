# Cross-AI Plan Review — Phase 20.1 (Round 3)

## Gemini Review

This is an adversarial review of Phase 20.1 (Plans 01–04). The plans are generally robust, but there are four remaining gaps—one critical data corruption hazard, one tick-loop crash risk, one confusing test-authoring instruction, and one logic clarification.

Here is the Round 3 review:

### 1. Plan 01 (Task 2) — CRITICAL: SENSOR `CellEntry` Re-expression Leak
**The Flaw:** In `buildLocomotorCells`, the plan instructs the executor to re-express the SENSOR cell's coordinate into a LOCOMOTOR-relative `Coord.Relative(wrappedDx, wrappedDy)` and then dedup via `putIfAbsent` using the new coordinate as the map *key*. However, the plan fails to explicitly instruct the executor to wrap the new coordinate in a **new `CellEntry`** for the map *value*.
**The Consequence:** If the executor uses the *original* `CellEntry` as the map value, `entry.coord()` will still return the old coordinate (relative to the SENSOR). The codec will serialize the old coordinate, and the client will receive fundamentally broken vision frames. 
**The Fix:** Explicitly mandate in Task 2: *"Wrap the re-expressed coordinate in a new `CellEntry` (e.g., `new CellEntry(newCoord, entry.envState())`) before inserting it as the map value. Do NOT insert the original `CellEntry`, or the frame will carry SENSOR-relative coordinates to the wire."*

### 2. Plan 04 (Task 1) — CONFUSION: Misunderstanding the 26-bot Loop 
**The Flaw:** The plan instructs the executor to *"have the 26-bot loop SKIP any cell that is already occupied"* to avoid colliding with the reserved composite block. 
**The Consequence:** The 26-bot loop in `GoldenTraceEquivalenceTest.driveScenario` does NOT manually pick coordinates; it iterates bot indexes and calls `handler.attemptPlacementForTest()`. `attemptPlacementForTest` *already* searches for and guarantees a random **unoccupied** cell. If an executor tries to inject manual `if (occupied) continue;` skip logic into the loop, they will either fail to implement it or accidentally reduce the total bot count (breaking the baseline structure).
**The Fix:** Remove the instruction to modify the 26-bot loop's skip logic. Rewrite to: *"Seed the composite FIRST. Because `attemptPlacementForTest` inherently searches for empty cells, it will naturally avoid your newly occupied composite cells without any loop modifications. Just assert collision-free status AFTER the loop to prove the reserved coords survived."*

### 3. Plan 01 (Task 2) — CRASH HAZARD: Blind `.get()` on `Optional`
**The Flaw:** The plan pseudo-code explicitly instructs: `getComposite(compositeId).get().getMemberIds()`.
**The Consequence:** If the entity registry and composite registry ever fall out of sync momentarily (e.g., during complex teardown, death processing, or race conditions), calling a blind `.get()` on an empty `Optional` will throw a `NoSuchElementException` and crash the entire tick loop for all bots.
**The Fix:** Instruct the executor to safely guard the Optional: *"Guard the composite lookup with `Optional.isEmpty()`. If the composite is missing from the registry, fallback safely by returning just the LOCOMOTOR's own radius-1 adjacency."*

### 4. Plan 03 (Task 2) — LOGIC FLAW: Duplicate Directions in `rankDirections`
**The Flaw:** The plan specifies that `rankDirections` must return *"at least 3 DISTINCT numpad-valid directions"*. However, `decideFullAuthority`'s cascade (which this logic reuses) simply evaluates cells. If there are 5 nutrients located to the `NORTH`, the raw classification stream will yield `NORTH` 5 times.
**The Consequence:** If the executor simply returns the mapped directions, the IRV ballot will waste ranks on duplicates (e.g., `['8', '8', '8']`). 
**The Fix:** Explicitly remind the executor to filter out duplicates during the ranking phase: *"Ensure the stream of directions returned by `rankDirections` is explicitly filtered for uniqueness (e.g., using `.distinct()` or a `Set`), because multiple targets can lie in the exact same direction."*

### HIGH-ish / MEDIUM — Plan 02: wrapped-offset tie-break is a no-op; seam test is vacuous
*(Plan 02, Task 2 action + Task 1 torus-seam test + success_criteria)*

`MAX_REPRODUCER_SEARCH_RADIUS = 5`. Grid 16 → `dim/2 = 8`. Candidate offsets `dx,dy ∈ [-5,5]`. For every `|d| ≤ 8`: `floorMod(d,16)` then `(raw <= 8 ? raw : raw-16)` returns **`d` unchanged**. So `wdx == dx` and `wdy == dy` for ALL candidates. The sort key on "POST-wrap normalized offsets" is **byte-identical to a raw-offset sort** on any 16-grid, at any placement, seam or not.

Consequences:
- The "torus-seam edge-adjacency determinism" test (REPRODUCER at (1,1)/(0,0)) **cannot distinguish wrapped from raw** — it passes for a plain `dx*dx+dy*dy, dy, dx` raw sort. The plan's claim ("this run MUST exercise the seam so a raw-offset sort would differ from a wrapped-offset sort") is **false**. Offset wrapping only diverges when `|offset| > dim/2`, which needs `maxRadius > 8` — impossible at 5.
- This is a **vacuous test** (your own rule: "a test that always passes is theatre") presented as the highest-value gate, plus dead normalization code. Round-2 ADDED this; round-3 should remove or honestly re-scope it.
- No correctness impact — raw-offset sort is equally deterministic, golden trace stable either way. The cost is false confidence + complexity.

Fix: either (a) drop the wrapped machinery, use raw `dx*dx+dy*dy, dy, dx` (identical result, less code, honest), keep ONE plain dual-run determinism test; or (b) if you insist on wrapped for future-proofing larger search radii, **delete the claim that the seam test pins wrapped-vs-raw** and label the normalization "no-op at current radius, guards a future `maxRadius > dim/2`."

Note: wrapped normalization IS meaningful in **Plan 01** (composite diameter can approach `dim/2`), so this is specifically a Plan-02 mis-port.

### MEDIUM — Plan 01: union re-expression "and wrap" underspecified → cross-seam dedup miss
*(Plan 01, Task 2 action — any-Coord→relative helper)*

Helper: "add the `relativeTo(locoPos, sensorPos)` offset and wrap." The **summed** offset `(sensorCellRel + sensorFromLoco)` can exceed `dim/2` for a spread composite (sensorFromLoco up to ~7, +2 window = 9 on a 16-grid; shortest form is −7). If the helper `floorMod`s or leaves the naive sum instead of re-normalizing to the toroidal-shortest `(raw <= dim/2 ? raw : raw-dim)` form:
- The same absolute cell contributed by two SENSORs on opposite sides of the seam (or by a SENSOR vs adjacency) gets **different keys → fails to dedup → appears twice**, non-deterministically depending on which SENSOR's path crosses the seam.
- Emitted coord may not match what `relativeTo`/HeuristicBrain expects for that cell.

No current test forces a summed offset past `dim/2` (all placements tight). Clamp-to-±63 won't fix it (9 ≠ −7, both ≤63). 

Fix: pin that the helper **canonicalizes the final summed offset through the `relativeTo` normalization** (not bare floorMod), and add a test with a SENSOR placed so a window cell's loco-relative position crosses `dim/2`.

### H2: Plan 02 tie-break sort key — `wdx`/`wdy` not effectively final in the illustrative lambda (Plan 02, Task 2)

**Severity: LOW**

The task pseudo-code shows:
```java
// inside the offset-generation loop:
int rdx = Math.floorMod(dx, w); int wdx = (rdx <= w/2) ? rdx : rdx - w;
```

**Recommendation**: Add a one-sentence note in Task 2's action: "Because wdx/wdy are not effectively final in a loop, store them as fields in the candidate record/tuple before sorting, or compute them inside the sort comparator from the raw (dx,dy) and the grid dims."

### H3: Phase-level — no test covers "LOCOMOTOR near torus seam, SENSOR contribution re-expressed across the seam" (Plan 01)

**Severity: MEDIUM**

The Plan 01 tests cover:
- SENSOR NW of LOCOMOTOR (negative coords) ✓
- SENSOR adjacent (self-cell filter) ✓
- Multiple overlapping SENSORs (dedup + sort) ✓

But none of the test scenarios places the LOCOMOTOR near a torus seam such that a SENSOR cell wraps around the torus. For example: LOCOMOTOR at (0,0) on a 16×16 grid, SENSOR at (0,2). A cell at (15,0) might be in the SENSOR's 5x5 window but, when re-expressed relative to the LOCOMOTOR, the shortest-path wrapped offset is NOT `(sensorDx + sensorPos.x - locoPos.x)` (raw). It's the toroidal shortest-path offset.

The `relativeTo` helper handles this correctly, and `buildCellEntries` already produces correct coords from the SENSOR's perspective. But the re-expression step:
```
relativeSx = relativeTo(sensorPos, sensorCellPos)  // cell's dx from SENSOR
// then add sensorPos - locoPos offset:
finalDx = relativeSx.x + relativeTo(locoPos, sensorPos).x
```
could be wrong when re-expressing across a seam, because `relativeSx` is a wrapped offset from the SENSOR's perspective, and adding another wrapped offset isn't the same as computing the direct wrapped offset from LOCOMOTOR to the cell.

**The correct approach**: Re-express each SENSOR cell entry by computing the cell's absolute position (from SENSOR's absolute position + SENSOR-relative offset), then computing the direct relative offset from LOCOMOTOR to that absolute position using `relativeTo`. The plan mentions the helper concept but doesn't specify whether it uses the direct-path or offset-addition-path approach.

**Recommendation**: Add a seam-wrap scenario to SensorStitchedPerceptionTest: LOCOMOTOR at (0,0), SENSOR at (0,2), nutrient at (15,0) (one cell west of seam, in SENSOR's 5x5 when wrapped). The shortest path from LOCOMOTOR(0,0) to (15,0) wraps to dx=-1. Assert the nutrient appears at Coord.Relative(-1,0) in the LOCOMOTOR frame. This pins the re-expression as direct `relativeTo(locoPos, absoluteCellPos)`, not a composed offset addition.
