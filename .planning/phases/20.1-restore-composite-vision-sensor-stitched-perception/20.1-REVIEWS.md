# Critical Review: Phase 20.1 (Restore Composite Vision)

Here is a structured, adversarial review of the Phase 20.1 implementation plans (01–04). While the plans are generally well-researched and structurally sound, there are several blind spots, particularly regarding performance (critical for your v3.0 Scale Engineering milestone) and edge-case correctness.

## 1. Performance & Scale Risks (Critical for v3.0)

**A. REPRODUCER Auto-Place causes unnecessary GC/CPU burn (Plan 02)**
*   **The Flaw:** Plan 02 instructs `nearestFreeCell` to generate up to 120 coordinate pairs, instantiate objects/tuples for each, and invoke `Collections.sort` with a complex comparator **every single time** a REPRODUCER attempts to bud.
*   **The Impact:** Under high density (1000+ bots, a key goal of v3.0), mass reproduction events will generate massive garbage and spike CPU usage purely to sort static relative offsets.
*   **The Fix:** The `(dx, dy)` offsets in the `[-5, 5]` bounding box and their toroidal-normalized distances *never change*. Compute and sort this array of 120 offsets **statically once** at class load. At runtime, `nearestFreeCell` should just iterate through the pre-sorted static array, apply `Math.floorMod(origin + dx)`, and check for a free cell. Zero allocations, zero runtime sorting.

**B. Log Spam DoS from `Coord.Relative` Clamping (Plan 01)**
*   **The Flaw:** Plan 01 dictates clamping relative coords to ±63 and emitting a `log.warn` (matching `buildRosterIfChanged`).
*   **The Impact:** If a composite is stretched across a torus boundary bug, or just unusually large, a SENSOR's 5x5 grid (25 cells) will be clamped. This means **25 `log.warn` emissions per SENSOR, per tick**. This will lock up the I/O thread and cause severe tick drift.
*   **The Fix:** Downgrade to `log.debug`, or rate-limit the warning to log once per composite per tick.

## 2. Functional & Correctness Blind Spots

**A. `hasOccupant()` vs `isEmpty()` Discrepancy (Plan 02)**
*   **The Flaw:** Plan 02 uses `!worldGrid.getCell(tx,ty).hasOccupant()` as the free-cell predicate. 
*   **The Impact:** The method it replaces (`findEmptyAdjacentCell`) uses `.isEmpty()`. If the environment features rocks, walls, or toxins, `hasOccupant()` might only check for living entities, completely ignoring environmental obstacles. The REPRODUCER could spawn a bud *inside a rock*.
*   **The Fix:** Explicitly verify the contract of `WorldGrid.Cell`. If `.isEmpty()` is the safe check that guards against environmental hazards, use `.isEmpty()`.

**B. Ghost SENSOR Vision Stitching (Plan 01)**
*   **The Flaw:** Plan 01 iterates `getMemberIds()`, gets `sensorPos`, and blindly builds a 5x5 vision grid from that position.
*   **The Impact:** If a SENSOR member dies, but the `CompositeRegistry` hasn't been purged yet (due to tick execution order), the LOCOMOTOR might stitch vision from a dead SENSOR. Worse, if another entity walked into that `sensorPos`, the LOCOMOTOR will stitch a 5x5 grid centered around a foreign entity.
*   **The Fix:** Before calling `buildCellEntries(sensorPos, ...)`, assert that the occupant of `sensorPos` is actually the exact entity ID of the SENSOR member you are iterating over.

**C. SENSOR Threat Blindness in `decideFullAuthority` (Plan 03)**
*   **The Flaw:** The LOCOMOTOR evaluates threats based on distance to *itself*. A predator 1 cell away from a SENSOR, but 5 cells away from the LOCOMOTOR, will be parsed as a `dist=6` threat.
*   **The Impact:** The priority cascade in `decideFullAuthority` deprioritizes distant threats. The LOCOMOTOR will ignore the predator currently eating its SENSOR.
*   **The Fix:** The plan accepts this as a consequence of reusing `decideFullAuthority`. However, since this directly undermines the survival value of SENSORs (D-06), this semantic limitation must be formally documented as tech debt, or the cascade logic should be tweaked to prioritize threats based on their proximity to *any* SENSOR cell.

## 3. Testing & Determinism Gaps

**A. Golden Trace Overlap Risk (Plan 04)**
*   **The Flaw:** `seedCompositeWithSensorAndLocomotor` will place a new composite directly on the grid. Plan 04 says to invoke this "alongside the existing bonding pairs".
*   **The Impact:** The scenario also seeds 26 random bots. If the hardcoded placement of the new composite collides with the deterministically seeded random bots, the test will throw placement assertions or alter the emergence dynamics wildly.
*   **The Fix:** Ensure the `seedCompositeWithSensorAndLocomotor` uses a known-empty region of the grid (e.g., coordinates explicitly reserved and avoided by the random bot seeder). 

## Summary Recommendation
1. Update **Plan 02** to strictly require a statically cached, pre-sorted offset array for `nearestFreeCell`.
2. Update **Plan 01** to use `.isEmpty()` (if safer than `!hasOccupant()`), prevent log spamming on clamp, and verify SENSOR entity identity before stitching vision. 
3. Proceed with the plans once these execution gaps are patched.

## Summary

Overall, these plans are unusually detailed and mostly execution-ready. The decomposition is sensible: wire/perception first, REPRODUCER auto-place independently, brain consumption next, golden trace last. The strongest parts are the explicit red/green scaffolding, deterministic-order guards, and awareness that golden traces must be regenerated only after behavior settles. Main risks are around subtle coordinate semantics, test assumptions that may not match existing helper behavior, and a few places where plan text says “8-cell adjacency” while the existing `buildCellEntries(pos, 1)` may actually emit a 3x3 window depending on current implementation.

## Strengths

- Clear phase throughline: Plan 01 restores SENSOR-derived perception, Plan 03 consumes it, Plan 04 pins it under golden trace.
- Good dependency ordering for high-risk baseline churn: golden re-pin is correctly last.
- Strong determinism posture: explicit ordering tests, golden dual-run guard, seeded scenarios, and warning against unordered maps.
- Good no-protocol-change discipline: keeps `a|R|<numpad>` and avoids unnecessary codec churn.
- Good threat awareness for perception leakage: LOCOMOTOR-exclusive union and composite OVERCROWDED omission are explicitly tested.
- Validation strategy is strong: task-level tests, full-suite gate, and new tests for previously unpinned behavior.

## Concerns

- **HIGH: “8-cell adjacency” may not equal `buildCellEntries(pos, 1)`.**  
  Multiple tasks assume radius-1 means 8 cells, but existing `buildCellEntries` may include the center cell. The plans need to verify or explicitly change this. If center is included, D-01 is not actually implemented as specified.

- **HIGH: REPRODUCER auto-place tie-break is over-specified and potentially wrong near torus seams.**  
  Generating `dx/dy` in `[-5,5]` then applying `relativeTo` normalization is fine for 16x16, but the “post-wrap euclidean²” language can create duplicate target cells on small worlds or if radius approaches half-dimension. The plan should define duplicate handling and candidate uniqueness.

- **HIGH: Plan 01 does not explicitly test FEEDER/ATTACKER exclusion from SENSOR union.**  
  The threat model says this is mitigated, but Task 1 only clearly adds LOCOMOTOR, REPRODUCER, and OVERCROWDED assertions. A direct FEEDER/ATTACKER “does not see SENSOR-only cell” test should be mandatory.

- **MEDIUM: `sensorRadius=1` with cells outside radius is semantically odd.**  
  The codec allows it, but clients or future tests may treat `sensorRadius` as a bound. The plan should add a short code/Javadoc comment or test naming that documents “radius describes primary self-window, not full cells extent.”

- **MEDIUM: Golden trace scenario may perturb existing scenario density.**  
  Adding direct composite members plus nutrients to `driveScenario` could affect placement of the existing 26 bots, entity counts, formation timing, or collision patterns. That is acceptable if intentional, but the plan should reserve fixed, non-overlapping coordinates and assert placement success.

- **MEDIUM: Plan 02 depends semantically on Plan 01 but declares no dependency.**  
  Code-wise it can run independently, but D-02 is tied to REPRODUCER becoming passive. Parallel execution is probably okay, but the roadmap should mark the semantic relationship or declare `depends_on: ["20.1-01"]` if executors may run plans in arbitrary order.

- **MEDIUM: HeuristicBrain reuse risks duplicating complex scoring behavior.**  
  Plan 03 says reuse or extract `decideFullAuthority` logic, but does not require avoiding copy-paste drift. If copied, future behavior changes will diverge between FULL and LOCOMOTOR.

- **MEDIUM: LOCOMOTOR voting test may be too narrow.**  
  A single nutrient at `(0,2)` proves basic use of `Coord.Relative`, but not that SENSOR-union cells from Plan 01 flow end-to-end through `BotClient`. Unit scope is fine, but the golden-with-actions trace becomes the only integration guard.

- **LOW: Summary-file creation is specified but not validated.**  
  Each plan says create `20.1-0X-SUMMARY.md`; no acceptance criteria verify they exist.

- **LOW: `grep` acceptance criteria are brittle.**  
  Some checks enforce implementation shape rather than behavior. They are useful as guardrails, but should not substitute for behavioral assertions.

## Suggestions

- Add a mandatory assertion in Plan 01 that `buildCellEntries(pos, 1)` produces exactly the intended adjacency set. If center must be excluded, implement and test that directly.
- Add FEEDER and ATTACKER tests: place a SENSOR-only-visible nutrient and assert their frames do not contain that relative coordinate.
- Add duplicate-target handling to `nearestFreeCell`: collect candidates into a map keyed by target `Position`, keeping the best sort key before sorting.
- Add an explicit test that REPRODUCER auto-place does not deduct shared pool energy when no target is found, if that is the intended “pre-existing early return” semantic.
- In Plan 03, prefer extracting a shared private helper like `rankDirectionsFromCells(...)` rather than copying `decideFullAuthority` scanning logic.
- In Plan 04, assert direct composite fixture placement succeeds and uses coordinates isolated from existing seeded entities.
- Add one integration-style assertion, either in golden-with-actions or a focused test, proving a LOCOMOTOR session receives SENSOR-union cells and emits a non-random `V` vote from them.
- Tighten Plan 02 dependency metadata or add a note that it is code-independent but semantically paired with Plan 01.

## Risk Assessment

**Overall risk: MEDIUM.** The plan quality is high and the validation net is strong, but the phase changes core wire semantics, deterministic traces, role authority, and action resolution. The main residual risks are subtle: center-cell inclusion, toroidal coordinate ordering, accidental SENSOR leakage to non-LOCOMOTOR roles, and re-baselining golden traces over a hidden nondeterminism. With the suggested extra tests, this becomes close to low-risk execution.

## 2. Strengths

- **Source-grounded research.** Line numbers, method signatures, and seams verified against actual code. Rare and valuable.
- **Determinism treated as first-class.** Order-stability test (`frame1.cells().equals(frame2.cells())`) catches HashMap/unsorted-stream bugs at Wave-1 instead of deferring to the golden gate. Torus-seam edge case for REPRODUCER tie-break is a sharp, non-obvious catch.

## 3. Concerns

- **[HIGH] The brain never emits an action for non-LOCOMOTOR composite roles — research's REPRODUCER premise is wrong.** `HeuristicBrain.decide` (lines 96–103) returns `null` for any composite role `!= 0`. The research (Q4, Pitfall 4) repeatedly asserts "the REPRODUCER's bot sends `a|R|<numpad>`." It does not. So in live operation, `resolveReproducerBud` is **never reached by heuristic bots** — it's only driven by `GoldenTraceWithActionsTest`'s hand-injected `R` (line 435). Plan 02 is therefore refactoring a path that is already behaviorally dormant. The work is *correct* and the trace shift is *real*, but the D-02 framing ("REPRODUCER becomes passive consistent with D-01") implies a behavior change that doesn't exist — it was already inert. **Impact:** no functional regression, but no plan verifies composite reproduction ever actually fires end-to-end. Flag so it isn't mistaken for live capability.

- **[HIGH] Negative-coord dedup key can silently corrupt the union, and no Plan-01 test catches it.** PATTERNS suggests keying the dedup map on `(unionDy << 16 | unionDx)`. With relative coords in ±63, a negative `dx` sign-extends across the high bits and collides/corrupts `dy` (e.g. `dx=-1` → `0xFFFFFFFF`). Critically, the **order-stability test cannot detect this** — a deterministically-wrong key produces equal output both runs. The monotonic-widening test only catches it if a collision happens to drop enough cells. Fix: key on the `Coord.Relative` record itself (value equality, `coordFor` already produces it) or mask each axis to 16 bits. Plan 01's acceptance criteria grep for `LinkedHashMap` + a sort but **do not verify key correctness**.

- **[MEDIUM] Plan 03's "reuse `decideFullAuthority` scoring" understates a genuinely new build.** `decideFullAuthority` is an early-returning cascade that emits *one* action with verb-switching (`A` for adjacent prey, `E` for nutrient, `M` otherwise). It does **not** produce a ranked direction list. Turning its prey/predator/nutrient scoring into a 3-rank IRV ballot (predators as repulsion, prey/nutrient as attraction, top-3 distinct directions) is new logic, not a copy. Plan 03 calls it "extract the shared scan / capture the ordered direction preference" — hand-wavy for the riskiest code in the phase. The test pins only `charAt(0)=='8'` for one nutrient + a weak predator negative — thin pinning for a fuzzy heuristic.

- **[MEDIUM] V-ballot distinctness/validity not addressed.** The current `topThreeDirections` uses Fisher-Yates → 3 *guaranteed-distinct* numpad digits. A scoring-derived fill could produce duplicates or fewer than 3 directions. If `PerceptionCodec` validates `V` requires 3 distinct numpad digits, a scored ballot could be malformed and rejected. Plan 03 says "fill from remaining directions… fall back to `topThreeDirections`" but never states the distinctness invariant or checks the codec's `V` arg constraint. Verify and pin it.

- **[MEDIUM] D-06 is proven only with synthetic frames — end-to-end path untested.** `HeuristicBrainLocomotorTest` hand-builds `TickFrame` with `List.of(nutrient @ Coord.Relative(0,2))`. It never consumes Plan 01's actual `TickBroadcaster` output. So nothing tests the full chain SENSOR→union→brain→ballot. The golden trace pins *bytes*, not *steering*. "Demonstrably steers using SENSOR-derived cells" is demonstrated with fabricated cells, not real ones. Consequently Plan 03's `depends_on: ["20.1-01"]` is arguably spurious for the unit test (it mocks the frame) — though harmless.

- **[LOW] D-01 FEEDER/ATTACKER frame-shaping has no consumer.** The brain ignores FEEDER/ATTACKER (returns `null`). So giving them 8-cell adjacency + OVERCROWDED=0 is pure wire/golden-trace correctness with zero behavioral observer this phase. Fine, but worth stating so it's not assumed to drive bot behavior.

- **[LOW] OVERCROWDED omission must thread `isCompositeMember=true` into the SENSOR-window `buildCellEntries` call too.** `buildLocomotorCells` calls `buildCellEntries` twice — own adjacency *and* each SENSOR's 5×5. Both must pass the composite flag, or union cells re-leak OVERCROWDED via the SENSOR's `envStateFor` (computed relative to `sensorPos`). Plan 01 says "thread the flag down" generally but doesn't call out the second (union) call site explicitly. The D-04 test iterates `frame.cells()` so it *would* catch this — but only if the dense-neighbourhood is placed within a SENSOR window, not just around the LOCOMOTOR. Make the test scenario explicit.

- **Scope discipline**: `SENSOR_PLUS_1` buff widening is explicitly deferred; REPRODUCER codec contract cleanup is deferred; no new packages. The "deferred ideas" section in research is a model of restraint.
- **STRIDE threat model**: Even for a phase with no new wire input, threats T-20.1-01 through T-20.1-03 (info disclosure via union leakage, OVERCROWDED bleed, wire overflow) are correctly identified and mitigated — the assertion that FEEDER/ATTACKER frames don't receive the union is a concrete verification gate.

## 3. Concerns

### HIGH

**H3.1 — `buildCellEntries` signature change: double-duty ambiguity in the LOCOMOTOR path**

Plan 01 says to thread `isCompositeMember` through `buildCellEntries` → `envStateFor`. In the LOCOMOTOR path, `buildLocomotorCells` calls `buildCellEntries` twice:
1. `buildCellEntries(locoPos, 1)` — own 8-cell adjacency
2. `buildCellEntries(sensorPos, PERCEPTION_RADIUS)` — each SENSOR's 5x5 window

Both need `isCompositeMember=true` (the LOCOMOTOR's entire frame is a composite member frame, and D-04 says OVERCROWDED=0 for all cells in it). The plan's prose says "thread an isCompositeMember boolean from buildTickFrame down" — but doesn't explicitly call out that the SENSOR-window `buildCellEntries` invocations inside `buildLocomotorCells` must also pass `isCompositeMember=true`. If only the adjacency call passes it and the SENSOR-window calls don't, union cells would retain OVERCROWDED from the D-40 expression (they'd be built as non-composite cells), creating an inconsistency within a single frame.

**Mitigation**: Plan 01 Task 2's acceptance criteria includes checking that `grep -c "cached & ~BIT_OVERCROWDED"` appears in the codebase. But it can't distinguish which call sites pass `true`. Add an explicit acceptance criterion in Plan 01 Task 2: the union-construction call to `buildCellEntries(sensorPos, PERCEPTION_RADIUS, isCompositeMember=true)` must be covered by the D-04 OVERCROWDED-always-0 test — meaning the test places a nutrient/entity in the SENSOR's 5x5 at a cell that is *also* overcrowded from the LOCOMOTOR's perspective, and asserts bit 0 is 0 in that cell entry.

**H3.2 — GoldenTraceWithActionsTest re-baseline: potential RNG-state divergence across runs**

Plan 03 changes `decideLocomotor` to fill unfilled ballot slots with `topThreeDirections(rng)` fallback. The number of RNG calls per tick now depends on how many meaningful directions the priority cascade produces. If the cascade produces different counts on different ticks (normal, since cell configurations change), the RNG draw sequence is different from the pre-change sequence. This is deterministic per-run (same ticks → same cascade → same RNG calls), so dual-run equivalence should hold. *However*, the `GoldenTraceWithActionsTest` re-baseline involves regenerating the JSON, then re-running — if the RNG state is identical across the two runs, it passes. The failure mode is: the second run produces a different digest because something is non-deterministic (bot action timing, composite formation timing, etc.).

The plan acknowledges this via T-20.1-09 (masked non-determinism halt) but only for the equivalence test, not for the with-actions test. The with-actions test has `bonding-probability=1.0` and composites form probabilistically — formation timing is deterministic, so this should be fine. But it's worth an explicit check: `GoldenTraceWithActionsTest` dual-run equivalence must pass before accepting the re-pinned baseline, same as the equivalence test. Plan 04 Task 2 mentions this but separates the two tests' re-baseline procedures — add an explicit gate: the with-actions test's own `mapA == mapB` assertion passes on the pinning run.

**H3.3 — `GoldenTraceEquivalenceTest.seedCompositeWithSensorAndLocomotor`: SENSOR member needs a bot session to be captured**

The golden trace captures per-session digests from `botRegistry.getSnapshot()`. Plan 04 Task 1 says to "Register a bot session for the LOCOMOTOR member" but does **not** register a session for the SENSOR member. Under D-01, the SENSOR receives a PASSIVE minimal frame — that frame format shift (from today's minimal form, which already exists) should ideally be captured in the golden trace. Not registering the SENSOR session means the minimal-form frame is not captured under the equivalence gate.

This is medium-criticality because `CompositePerceptionTest` covers the SENSOR minimal form. But the golden trace is supposed to be comprehensive. The minimal form's exact byte shape — specifically the absence of `s`, `p`, `r`, `e` blocks when `sensorRadius=0` — is worth pinning under the gate.

### MEDIUM

**M3.4 — `tierOf()` REPRODUCER movement: what about the existing AUTHORITY_LITE path for REPRODUCER?**

Currently `tierOf` maps REPRODUCER → `AUTHORITY_LITE` (sensorRadius=1). Plan 01 moves REPRODUCER to `PASSIVE`. This means the REPRODUCER no longer receives a vision block. The plan explicitly mentions this in the action section ("REPRODUCER joins SENSOR/DEFENDER on the PASSIVE branch"). Good. But existing tests that assert REPRODUCER gets `AUTHORITY_LITE` (the `CompositePerceptionTest` likely has `reproducerMemberReceivesAuthorityLite`) need to be *updated*, not just superseded. Plan 01 Task 1 says to add a REPRODUCER-passive assertion — but does it also say to remove/update the existing AUTHORITY_LITE assertion for REPRODUCER? It doesn't explicitly say so. If the existing test exists, it will fail when REPRODUCER moves to PASSIVE, and the plan should call this out.

**Recommendation**: Check if `CompositePerceptionTest` has an existing `reproducerMemberReceives*` test and explicitly list it in Plan 01 Task 1's "files to update" or acceptance criteria.

**M3.5 — `buildCellEntries` signature: all callers audit**

`buildCellEntries` is private to `TickBroadcaster`. The plan adds a parameter `isCompositeMember`. The existing callers (line 386 for the main path, and recursive calls within `buildCellEntries` itself for env-supplement cells) need updating. The plan doesn't enumerate all callers. This is low-risk (the compiler catches them), but the acceptance criteria could include a grep: `grep -c "buildCellEntries(" src/main/java/com/paralife/websocket/TickBroadcaster.java` should match the expected count.

**M3.6 — `CompositeRegistry.getComposite()` returns `Optional.empty()` if composite was dissolved mid-tick**

During tick processing, a composite could be dissolved (all members died) in an earlier phase. `buildLocomotorCells` calls `compositeRegistry.getComposite(compositeId)` which could return empty. The plan's action says "if empty, fall back to radius-1 only" — this is correct. But the plan should also handle the case where the composite exists but some SENSOR members are dead (their grid cells now hold a different occupant or are empty). The plan handles this via the `sc.occupant() instanceof CompositeMember cm2 && cm2.role() == Role.SENSOR` check — if the member died, the grid cell won't have that CompositeMember anymore. This is correct.

**M3.7 — HeuristicBrain plan scope: "extract shared scan into private helper" is a non-trivial refactor**

Plan 03 Task 2 says to "reuse the decideFullAuthority classification + scoring (extract the shared scan into a private helper, or call the cascade directly)". `decideFullAuthority` is ~130 lines of scanning logic. Extracting a shared helper that both `decideFullAuthority` and `decideLocomotor` call is a moderate-refactor-with-test-coverage situation. The plan's acceptance criteria only check that `decideLocomotor` references `frame.cells()` — not that the extraction doesn't break `decideFullAuthority`. The existing HeuristicBrain tests should catch regressions, but the plan should explicitly confirm the existing brain test suite stays green as an acceptance criterion (it says "Existing HeuristicBrain tests still pass" at the bottom of the criteria, which is good).

### LOW

**L3.8 — REPRODUCER max radius of 5 on a 16×16 test grid covers 47% of cells**

On `GridConfig(16, 16)`, `MAX_REPRODUCER_SEARCH_RADIUS=5` means the search box is 11×11 = 121 cells (~47% of the 256-cell torus). This is fine for correctness (still bounded), but tests that assert "nearest free cell" might accidentally find a cell that is farther than expected if the test doesn't control occupancy tightly. The `ReproducerAutoPlaceTest` should fill most cells in the search box to ensure the "nearest" assertion is testing actual distance ordering, not just "first found."

**L3.9 — Golden-trace baseline files are named `golden-trace-phase19.json` and `golden-trace-with-actions-phase19.json`**

These file names embed "phase19" and will be misleading after Phase 20.1 lands (the baselines will reflect post-20.1 semantics). The plan doesn't address renaming. This is cosmetic but worth mentioning — if the intent is to freeze phase-19 semantics as "pre-SENSOR-stitching" and create phase-20.1 baselines as new files, that's a different strategy from re-pinning in-place. Re-pinning in-place is the plan's approach and is fine, but consider a follow-up task to rename or add a comment header in the JSON file noting it was re-pinned at Phase 20.1.

**L3.10 — Missing test: LOCOMOTOR with NO SENSOR members → 8-cell-only (near-blind)**

The D-01 amendment says this is intentional ("near-blind"), but no test explicitly asserts that a LOCOMOTOR-in-a-composite-with-zero-SENSORs gets exactly 8 cells (radius-1 adjacency only) and does NOT get a 5x5. This is implicitly covered by the `SensorStitchedPerceptionTest` monotonic-widening test (add SENSOR → more cells), but it doesn't test the baseline count. Add a one-line assertion in the monotonic test: `frameWithoutSensor.cells().size() <= 8` (the LOCOMOTOR's own adjacency) to make the near-blind contract explicit.

## 5. Risk Assessment

**Risk Level: LOW**

**Justification**: The plans are exceptionally well-researched — every seam, interface, and pitfall is verified against live source code. The dependency ordering is correct, the TDD approach guarantees contract pinning before implementation, and the golden-trace re-baseline strategy is defensively designed (halt-on-non-determinism, dual-run guards, test-driven baseline generation). The three HIGH concerns (H3.1–H3.3) are narrow, easily fixable gaps in the execution detail, not architectural problems. The phase introduces no new wire protocol, no new concurrency paths (single-threaded tick pipeline is unchanged), and no new external dependencies. The STRIDE model correctly identifies the three trust boundaries and mitigates each with concrete verification gates. Execution risk is concentrated in Plan 03's shared-scan extraction (M3.7) and Plan 04's re-baseline procedure (H3.2), both of which the existing test suite can catch. The plans achieve the phase goal — restoring the P12 sensory-organ model — with high fidelity to the locked decisions.
