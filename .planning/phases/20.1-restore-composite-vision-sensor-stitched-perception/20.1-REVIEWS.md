# Cross-AI Plan Review — Phase 20.1 (SENSOR-stitched perception)

This review round covers the post-replan plans (after the prior cross-AI round was incorporated
via commit 09bc458). Three independent models reviewed all four plans.

---

## Codex Review

## Summary

The four plans are unusually thorough and mostly execution-ready. They cover the core phase goal: restoring SENSOR-stitched composite perception, making REPRODUCER passive/server-placed, teaching LOCOMOTOR brains to consume the richer frame, and re-pinning deterministic golden traces. The strongest parts are the red-first test design, explicit determinism gates, and attention to information-leak risks between composite roles. The main risks are over-specification in a few places, a questionable performance requirement in Plan 02, and some possible ambiguity around coordinate/`CellEntry` re-expression in Plan 01.

---

## Plan 20.1-01 — TickBroadcaster SENSOR Union

### Strengths

- Strongly pins the intended D-01/D-03/D-04 semantics with targeted tests before implementation.
- Correctly treats SENSOR union as LOCOMOTOR-exclusive and tests FEEDER/ATTACKER no-leak behavior.
- Good coverage of determinism: list equality, stable ordering, negative-coordinate dedup, signed-key collision guard.
- Correctly calls out that `OVERCROWDED` must be omitted for both LOCOMOTOR adjacency and SENSOR-contributed union cells.
- Good security/information-disclosure framing for per-role vision.

### Concerns

- **MEDIUM:** The plan assumes re-expressing SENSOR `CellEntry` coordinates is straightforward, but the implementation must handle whatever coordinate type `buildCellEntries` emits, especially if radius-1 entries use `Coord.Numpad` while radius-2 uses `Coord.Relative`.
- **MEDIUM:** Sorting mixed adjacency and union entries after dedup may change the historical ordering of normal radius-1 cells. That may be acceptable, but the plan should explicitly acknowledge this as intentional golden-trace churn.
- **LOW:** The `cells().size() <= 8` baseline is slightly weaker than “exactly 8” for an empty neighborhood if `buildCellEntries` always emits the full Moore ring. Some tests do assert exact cardinality, but acceptance criteria emphasize `<= 8`.
- **LOW:** The plan is very prescriptive on grep checks. Useful for agents, but some checks could fail on a clean equivalent implementation.

### Suggestions

- Add an explicit helper contract for converting any `Coord` into LOCOMOTOR-relative `(dx, dy)`.
- Require an assertion that no LOCOMOTOR frame exceeds `PerceptionCodec.MAX_S_ENTRIES`.
- Prefer “exactly 8” for the no-SENSOR empty-neighborhood test unless existing env-only suppression makes that impossible.
- State whether final sorted order intentionally supersedes prior row-major adjacency order.

### Risk Assessment

**MEDIUM.** The design is correct and well-tested, but coordinate re-expression and role-scoped `OVERCROWDED` threading are easy to get subtly wrong.

## Plan 20.1-02 — REPRODUCER Auto-Placement

### Strengths

- Correctly removes bot-chosen direction from server placement while preserving the codec contract.
- Includes good deterministic tests: nearest free cell, tie-break, seam behavior, bounded skip.
- Explicitly preserves `eligibleCellIndex.notifyChanged`.
- Correctly frames this as dormant-path cleanup, avoiding overclaiming live behavior.

### Concerns

- **HIGH:** The “statically pre-sorted offsets” requirement is overcomplicated and internally awkward because toroidal normalization depends on grid dimensions. If worlds can vary in size, cached offsets must be keyed by `(width,height)` or built per `ActionResolver` instance after grid construction. A single static order is unsafe unless grid dimensions are globally fixed.
- **MEDIUM:** The plan says sort by post-wrap-normalized offsets, but candidate offsets are only `[-5,5]`. On a 16x16 grid, raw and wrapped offsets are already the shortest offsets for that bounded box; seam behavior comes from applying `floorMod` to targets, not from changing the offset ordering. The test may not actually distinguish raw vs wrapped sorting.
- **MEDIUM:** “Zero per-bud allocation” may be premature optimization for 120 candidates. It adds complexity to a correctness-sensitive path.
- **LOW:** Bounded skip should explicitly assert shared pool energy is not deducted when no target is found.

### Suggestions

- Replace “static at class load” with “precomputed once per `ActionResolver` instance or cached per grid dimensions.”
- Make the primary requirement correctness and determinism; treat no per-bud sort/allocation as a nice-to-have unless profiling proves it matters.
- Add a direct test that the bot-supplied direction points to a valid but non-nearest cell and is still ignored.
- Add assertion that no child is spawned and pool energy is unchanged on bounded skip.

### Risk Assessment

**MEDIUM-HIGH.** The behavior is clear, but the precomputed-offset requirement risks introducing complexity and dimension-caching bugs.

## Plan 20.1-03 — HeuristicBrain LOCOMOTOR Voting

### Strengths

- Correctly closes the loop: SENSOR vision matters only if LOCOMOTOR consumes `frame.cells()`.
- Good test coverage for SENSOR-only food, empty fallback, valid ballot shape, and duplicate-rank prevention.
- Honest about accepted tech debt around threat distance from SENSORs.
- Keeps `decideFullAuthority` stable, reducing regression risk.

### Concerns

- **MEDIUM:** The plan says “flee predator > consume/chase prey > move toward nutrient,” but LOCOMOTOR can only vote movement, not consume/attack. The helper should translate all priorities into direction ranking, not inherit full-authority action semantics too literally.
- **MEDIUM:** Threat avoidance is underspecified. “Top rank is not predator’s direction” is weaker than “top rank points away when possible.”
- **LOW:** The test assumes `Coord.Relative(0,2)` maps to north `'8'`; the plan says to confirm sign convention, which is good, but this is a common failure point.
- **LOW:** Allowing `'5'` as codec-valid may be technically true, but for movement ballots it may be semantically poor if `Direction.fromNumpad('5')` is null or rest-like.

### Suggestions

- Define ranking scores explicitly: attractors positive toward their direction, predators negative for their direction and positive for opposite direction.
- Add a test where SENSOR-only food competes with a farther/nearer target to pin distance priority.
- Decide whether `'5'` should ever appear in a LOCOMOTOR IRV ballot. If not useful, exclude it from fallback despite codec validity.
- Add deterministic same-seed/same-frame assertion for `rankDirections`.

### Risk Assessment

**MEDIUM.** The plan achieves D-06, but movement-ranking semantics need care so it does not become a thin copy of full-authority behavior.

**MEDIUM.** The re-baseline process is sound, but direct fixture insertion can create large trace churn and must be carefully documented.

# Cross-AI Plan Review — Phase 20.1 (SENSOR-stitched perception)

## Overall Summary

These are unusually rigorous plans. The research and patterns docs planted the classic traps of this design (signed-shift dedup-key sign-extension, wrong-origin coordinate re-expression, golden-trace re-baseline laundering deterministic bugs into "truth"), and the plans **explicitly identify and gate every one of them** with dedicated tests. The dependency/wave ordering is correct (perception + action changes land before the re-baseline). The biggest soundness property of any golden-trace re-baseline — *refuse to re-pin if dual-run equivalence or semantic unit tests fail, push the non-determinism back to its origin* — is present and well-stated in Plan 04. The phase goal (restore the sensory-organ model so SENSORs produce LOCOMOTOR-consumable FOV) is achieved by the plan set.

My concerns are concentrated in two places: **over-engineering a provably-dormant code path (Plan 02)**, and **a few test-coverage gaps where a locked decision is implemented but not pinned** (D-04 for FEEDER/ATTACKER; the self-cell union artifact). One genuine ambiguity (does the with-actions golden test actually route V-votes through the brain?) should be resolved before execution because it changes whether Plan 03 affects that baseline at all.

---

## Plan 01 — TickBroadcaster per-role routing + SENSOR union + D-04

### Strengths
- **Sign-extension dedup-key trap caught and gated.** Research/patterns both suggested `(dy<<16)|dx` — the buggy signed form. Plan 01 forbids it explicitly and adds a NEGATIVE-COORD DEDUP test (SENSOR NW of LOCOMOTOR, distinguishable cell at negative `Coord.Relative`, asserted present exactly once). This is the single highest-leverage test in the phase and it exists.
- **Order-stability pinned via `List.equals` across two independent builds** — catches HashMap/unsorted-stream leakage at Wave-1, not at the golden gate.
- **Wrong-origin pitfall pinned numerically** (NUMERIC-ORIGIN test asserts the exact LOCOMOTOR-relative dx/dy of a SENSOR-only cell).
- **SENSOR-identity guard** (`occupant instanceof CompositeMember && role()==SENSOR`) correctly rejects a dead member or a foreign entity that walked onto the cell.
- Silent ±63 clamp matching `buildRosterIfChanged` is the right call (per-cell log on a 5×5 window = tick-drift spam).

### Concerns
- **MEDIUM — D-04 for FEEDER/ATTACKER is implemented but not directly tested.** D-04 omits OVERCROWDED for *LOCOMOTOR, FEEDER, ATTACKER alike*. The plan threads `isCompositeMember=true` through the line-386 generic path (which FEEDER/ATTACKER use), so it should work — but the only D-04 assertion is on a LOCOMOTOR union cell. The no-leak test proves FEEDER/ATTACKER *don't get SENSOR cells*; nothing asserts their *own* cells carry OVERCROWDED=0. Add one assertion to a FEEDER (or ATTACKER) frame iterating `cells()` for `(envState & 0x01)==0`.
- **LOW–MEDIUM — self-cell (0,0) leaks into the union, untested, will freeze into the baseline.** If a SENSOR is adjacent to the LOCOMOTOR, the SENSOR's 5×5 window *includes the LOCOMOTOR's own cell* (it's a non-center cell from the SENSOR's perspective). Re-expressed relative to LOCO that's `(0,0)`. Adjacency never contains `(0,0)` (LOCO skips its own center), so the union inserts it. The brain ignores it (`toDirectionInfo` returns null for 0,0), so it's harmless behaviorally — but it's a semantically odd "LOCOMOTOR sees itself" entry that no unit test covers and that Plan 04 will pin as truth. Recommend a one-line `if (reExpressedCoord == (0,0)) continue;` filter in `buildLocomotorCells`, plus an assertion.
- **LOW — "strictly widens" is asserted only for a constructed content case.** The must_have truth states adding a SENSOR *strictly* widens. Structurally this holds because `buildCellEntries` emits every ring cell regardless of content (so a SENSOR's outer ring always exceeds LOCO's 8-ring), but the test only exercises the nutrient-in-window case. Fine as-is; just note the general claim rests on `buildCellEntries` emitting empty cells — worth a one-line comment so a future change to that method doesn't silently break the invariant.

### Note (not a defect)
Dedup content is actually order-*invariant*: a given LOCO-relative coord maps to exactly one world cell, so two SENSORs covering it produce identical `CellEntry` content — `putIfAbsent` first-wins is a no-op on content. The **final explicit sort** is what guarantees output stability; the LinkedHashMap is belt-and-suspenders. Keep both (cheap), but the load-bearing guarantee is the sort, not the insertion order.

## Plan 02 — REPRODUCER server-side auto-place

### Strengths
- **Dormant-path framing is honest and load-bearing.** The plan states plainly that `resolveReproducerBud` is reached *only* by `GoldenTraceWithActionsTest`'s injected `R` action and that heuristic bots never emit `R`. This correctly reframes the work as golden-correctness + dead-code cleanup, not new live capability.
- Wrapped-offset (not raw-offset) tie-break with the canonical `relativeTo` normalization is the right correctness fix, and the **torus-seam determinism test** proves it.
- Distance-ordered (not first-found) nearest test — fills the inner box so "nearest" is a real distance assertion.

### Concerns
- **MEDIUM — the static pre-sorted-offset optimization is premature work on a dead path, and it introduces a correctness hazard the simple version doesn't have.** The justification is "avoid per-bud GC/CPU under 1000+ bots." But mass composite reproduction *never happens* — the path is dormant, runs only in one test, over ~120 candidates. The plan then permits a **static** cache of offsets normalized against `worldGrid` dims, lazily frozen on first use. A `static` field freezes the *first grid size seen in the JVM*; any test using a non-16×16 grid afterward gets wrong offsets — a latent cross-test bug created entirely by an optimization the dormant path doesn't need.
  - **Recommendation:** either (a) drop the pre-sort, use research Pattern 2's per-call generate-and-sort (trivial at 120 elements, zero shared state, matches the locked D-02 algorithm exactly); or (b) if you keep caching, mandate an **instance** field (ActionResolver is a singleton bean; tests construct fresh instances → safe re-init) and explicitly **forbid `static`**. The plan currently allows `static`.
- **LOW — D-02's nearest-Euclidean algorithm itself is locked by the user**, so the *algorithm* is not over-reach (don't simplify it to first-free-neighbor). My critique is scoped strictly to the pre-sort/caching machinery, not the search semantics.

## Plan 03 — HeuristicBrain LOCOMOTOR voting

### Strengths
- **Scope honesty** — explicitly flags this as new logic (ranked IRV ballot) vs `decideFullAuthority`'s early-returning single-action cascade, and the "prefer copying the scan over extracting a shared method if extraction risks regressing decideFullAuthority" guidance is the correct risk posture.
- Ballot-validity-by-construction (3 chars, each '1'–'9', distinct via `topThreeDirections` fallback skipping chosen) is pinned on food/threat/empty/multi-target scenarios.

### Concerns

The *existing* test passed with the old random-shuffle ballot, which proves the RNG is already seeded deterministically — so the new scored ballot is also reproducible. ## Plan 04 — Golden-trace re-baseline

### Strengths
- **Correct ordering** (wave 3, after 01/02/03) — re-baselining before the frame changes settle would churn digests mid-phase.
- **The anti-laundering guard is the standout.** Task 2 halts if the second run mismatches *or* either test's own dual-run `mapA==mapB` fails, forcing the non-determinism back to its origin plan rather than re-pinning churn. This is exactly the property that makes golden re-baseline trustworthy.
- **Reserved coords + asserted placement** (`trySetEntity` boolean asserted) prevents a silent collision with the 26 random bots from perturbing emergence — a collision fails loudly.
- Registers a session for the **SENSOR** member too, capturing its minimal-form digest under the gate (completeness most plans would miss).

### Concerns
- **MEDIUM — unverified premise: does `GoldenTraceWithActionsTest` route V-votes through `HeuristicBrain`, or inject fixed V frames?** Plan 04 asserts the with-actions baseline shifts because of "D-06 LOCOMOTOR V voting." That's only true if the test exercises the brain. If it injects raw action frames (as it does for `R`), Plan 03 has *zero* effect on that baseline and the rationale is spurious (the baseline still shifts — from D-01/D-04 frame reshape and D-02 — but not from V voting). This doesn't change *whether* you re-pin, but it changes the failure-diagnosis story in Task 2 ("if it mismatches, suspect the union/dedup/brain"). **Resolve before execution:** confirm the action source for V in that test.
- **LOW–MEDIUM — re-baseline can only be as sound as Plan 01's semantic tests.** A *deterministic* bug (the self-cell (0,0) artifact above; a stable-but-wrong coordinate) produces stable digests that freeze as truth. The dual-run guard cannot catch it — only Plan 01's NUMERIC-ORIGIN / NEGATIVE-COORD tests can. The chain is sound *given* those tests are comprehensive; the (0,0) gap is the one currently-uncovered semantic case that would survive into the baseline. Closing the Plan 01 gap closes this.
- **LOW (cosmetic) — Task 1's verify gate** (`grep` for `SEEDER_REACHED_BASELINE_FORK` plus a negative grep for stack frames) is fragile. Functional, but a brittle acceptance signal.

## Plan 03: HeuristicBrain LOCOMOTOR voting from frame.cells()

### Suggestions
- Prefer extraction over copy if the executor can find a clean seam that doesn't change `decideFullAuthority`'s emitted action — a `classifyCells(Frame.TickFrame)` helper returning categorized lists would serve both paths without risk.
- Add an explicit assert/comment in the food-steer test confirming `fromDxDy(0, signum(2)) == '8'` so the sign convention is pinned at the test.

### Risk: LOW
Client-side logic with no wire-surface or server-state risk. The fallback paths are well-gated.

## Plan 04: Golden-trace re-baseline

**Summary:** Rigorous re-baseline procedure. Both baselines (equivalence and with-actions) are independently gated on their own dual-run equality. The new SENSOR scenario uses reserved/asserted coords with dual-session registration. Task 2's halt-if-non-deterministic policy is the correct safety valve.

### Strengths
- GoldenTraceWithActionsTest gets its *own* dual-run mapA==mapB gate, not inherited from the equivalence test — this catches per-run variance in the action path (REPRODUCER auto-place, LOCOMOTOR V voting) that the equivalence test's scenario might not exercise.
- Reserved coords + `trySetEntity` asserted return — a collision fails loudly, doesn't silently perturb emergence.
- SENSOR session registration requirement ensures the minimal-form (sensorRadius=0) digest is captured, not just the LOCOMOTOR stitched frame.
- Task 2 explicitly halts if either test's own dual-run mapA==mapB fails — won't launder non-determinism through re-pinning.
- The verify step `SEEDER_REACHED_BASELINE_FORK` in Task 1 is a clever guard against seeder-internal crashes that would otherwise silently pass compile-only checks.

### Concerns
- **MEDIUM** — The 26-bot random-seeded loop in `driveScenario` is deterministic but not trivial to audit for coordinate collision with the reserved composite block. The plan suggests two approaches (seed composite first + skip occupied, or hardcode a provably-unreachable region). The second approach is fragile (changing the RNG seed changes reachable coords); the first approach depends on the loop's collision-skip semantics. The plan should assert that the reserved block is collision-free *after* the 26-bot loop runs.
- **LOW** — The plan mentions extending `resetAll()` if Plan 01 added new TickBroadcaster state but leaves the check to execution-time. A stale-cache leak between the two golden traces (equivalence test and with-actions test in the same suite run) could cause different failures than single-test runs.
- **LOW** — The `SEEDER_REACHED_BASELINE_FORK` grep is fragile — if Gradle changes its output format or the test name changes, the grep silently fails and the verify "passes" vacuously.

### Suggestions
- Add an assertion after the 26-bot loop: for each reserved coordinate in the composite block, `assertThat(worldGrid.getCell(x,y).hasOccupant()).isFalse()` — the seeder runs *before* the loop, and this assertion verifies the loop didn't encroach.
- Consider having `resetAll()` in *both* golden test classes call `tickBroadcaster.clearStateForTest()` explicitly (even if the method body is currently empty) to prevent inter-test state leaks between the two golden test classes in a full-suite run.

### Risk: LOW
The re-baseline procedure is mechanical and well-guarded. The primary risk is non-determinism from plans 01-03, which Task 2's halt-on-mismatch policy catches.

### Agreed Concerns (2+ reviewers) — highest priority
1. **[HIGH consensus] Plan 02 static pre-sorted-offset optimization on a dormant path.**
   All three flag it. Codex rates HIGH; Claude/OpenCode MEDIUM. A `static` offset cache frozen against
   the **first grid dimensions** seen in the JVM is a latent cross-test correctness bug (any later
   non-16×16 grid gets stale offsets), and the optimization buys nothing on a path that runs only in
   one golden test over ~120 candidates.
   **Fix (Claude, cleanest):** drop the pre-sort and use per-call generate-and-sort (trivial at 120
   elements, matches locked D-02 algorithm), **or** if caching is kept, mandate an **instance** field
   and explicitly **forbid `static`**. The locked D-02 nearest-Euclidean *algorithm* is not the
   problem — only the caching machinery.
2. **[MEDIUM] Plan 01 coordinate re-expression / sign handling.** Codex flags mixed `Coord` types
   (radius-1 `Coord.Numpad` vs radius-2 `Coord.Relative`) needing a uniform "any Coord → LOCOMOTOR-relative
   (dx,dy)" helper. Claude pins the numeric-origin test as the load-bearing guard. Both want the
   re-expression contract made explicit. (Codex, Claude)
3. **[MEDIUM] Plan 04 reserved-coord block vs the 26-bot random seeder is brittle.** Both recommend:
   seed the composite first + skip occupied cells, then **assert the reserved block is collision-free
   after the seeder loop** — rather than relying on a "provably unreachable" hardcoded region that an
   RNG-seed change could invalidate. (Codex, OpenCode)
4. **[LOW] Plan 03 sign-convention pin `Coord.Relative(0,2) → north '8'`.** Both want the
   `fromDxDy(0, signum(2)) == '8'` mapping asserted/commented at the test to prevent a coordinate-sign
   reversal slipping through. (Codex, OpenCode)
