<objective>
Implement D-06: replace `HeuristicBrain.decideLocomotor`'s random-shuffle ballot with a real food/threat steering heuristic that reads `frame.cells()` — including the SENSOR-derived union cells now delivered by Plan 01. The LOCOMOTOR must demonstrably vote toward food (and away from threats) that are only visible through a SENSOR.

Purpose: Close the loop — SENSOR-extended FOV is worthless unless the brain consumes it. This is the behavioural payoff of the sensory-organ model.

SCOPE HONESTY (do not under-state): this is NEW logic, not a copy/extract. `decideFullAuthority` is an EARLY-RETURNING cascade that emits ONE action with verb-switching (`A`/`E`/`M`); it does NOT produce a ranked direction list. The new helper turns prey/predator/nutrient scoring into a 3-rank IRV ballot of DIRECTIONS ONLY (predators as repulsion, prey/nutrient as attraction by -distance, top-3 DISTINCT directions). It is a genuine build behind a named helper, gated by tests, not a mechanical extraction — and crucially it produces a movement-direction ranking, NOT consume/attack action verbs.

Output: Modified HeuristicBrain, new HeuristicBrainLocomotorTest. Depends on Plan 01 because the LOCOMOTOR frame must already carry SENSOR union cells as Coord.Relative entries for the brain to steer by them (the unit test mocks the frame, so the dependency is semantic correctness, not a compile dependency).

ACCEPTED TECH DEBT — SENSOR-DISTANCE THREAT AVOIDANCE (document in the summary; do NOT silently inherit): the reused threat/distance scoring measures distance from the LOCOMOTOR's own position. A predator adjacent to a far SENSOR (far from the LOCOMOTOR) is therefore scored as a distant, deprioritized threat — so the LOCOMOTOR will not strongly flee a predator currently eating its SENSOR. This partially undercuts the D-06 survival value of SENSORs (the SENSOR's tangible value in THIS phase is mostly food-seeking, not survival-from-distant-threat). The ROADMAP Phase 20.1 success criteria (verified) require SENSOR-stitched FOV, dedup/ordering, monotonic widening, and PASSIVE wire status — they do NOT require threat-via-SENSOR — so this is ACCEPTED for this phase (prioritizing threats by proximity to ANY SENSOR cell is a follow-up). Recorded here so it is a known limitation, not an unnoticed bug, and the THREAT-AVOID test below deliberately uses a NEAR predator (the food path is the in-scope SENSOR payoff).

REVIEW NOTE (round-2 consensus, Plan 03 [LOW]): two pins folded in — (a) the sign convention is pinned AT THE TEST with an explicit `fromDxDy(0, signum(2)) == '8'` assertion + comment; (b) rankDirections must NOT introduce a fresh `Random` (verified by grep). Plus the Codex note: the helper produces direction ranking, not full-authority action semantics.

REVIEW NOTE (round-3 consensus, Plan 03): two pins folded in. (C4, gemini #4) rankDirections MUST dedup the direction stream — multiple targets in the same direction (5 nutrients north) would otherwise emit `['8','8','8']`; apply `.distinct()` / a Set BEFORE building the IRV ballot, pinned by a NEW multi-same-direction test. (C5, codex) the THREAT-AVOID test is strengthened: in a PREDATOR-ONLY frame (no food/prey to confound the cascade) assert the top rank EQUALS the opposite/repulsion direction, not merely "not toward the predator" — a weak "not-toward" assertion can pass on fallback randomness or a stray nutrient preference. The SENSOR-distance threat limitation is recorded as accepted TD above (ROADMAP does not require threat-via-SENSOR).
