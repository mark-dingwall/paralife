## TD-20.1-A — SENSOR-window RockRun fidelity (expand to N RockSolo)

**Surfaced:** opencode (round 2), gemini + codex HIGH (round 3); recategorised to
accepted terrain TD by the operator's MVP lens.

**Finding:** When a SENSOR's 5×5 window contains ≥2 consecutive rocks, `buildCellEntries`
RLE-encodes them as a single `KindData.RockRun(direction, additionalCount)` at the run
starter (tail cells are flagged `consumed` and never emitted separately —
`TickBroadcaster.java:508-519`). Plan 01 copies `kind` verbatim and re-expresses only the
starter coord. The run `direction` is a step-direction RLE digit (its own convention, the
inverse of the coordinate numpad — TickBroadcaster:534-543) that is invariant under
coordinate-origin re-expression, so the common
case decodes correctly, BUT two narrow edge cases mis-handle the run:
1. A run crossing the LOCOMOTOR's `dim/2` boundary mid-run can mis-position tail rocks
   (the re-expressed starter + compass direction no longer tracks the toroidal-shortest
   path of the later rocks).
2. A run-tail cell coinciding with an adjacency / other-SENSOR entry can double-represent
   that cell (the tail is implied by the run AND present as a separate entry).

**Why deferred:** Rocks are non-actionable for the D-06 heuristic brain (`HeuristicBrain`
treats Rock as "no action target"); rock-relay fidelity is NOT a Phase 20.1 success
criterion (the criteria are SENSOR-stitched FOV, dedup/ordering, monotonic widening,
PASSIVE wire status). The edge cases require a SENSOR (post-formation role), a rock run in
its window, AND a seam-crossing/overlap coincidence — narrow. The phase ships the verbatim
copy (no data loss; the regression of substituting a single `RockSolo` for the starter,
which DROPS the tail rocks, is explicitly forbidden in Plan 01 Task 2).

**Fix sketch (when rock fidelity is required):** In `buildLocomotorCells`, when a SENSOR
entry's kind is `RockRun(dir, count)`, EXPAND it into `count + 1` individual rocks: for
`i` in `0..count`, compute the i-th rock's absolute position (`sensorPos` + starter offset
+ `i * stepForDir(dir)`), re-express each via the same direct
`relativeTo(locoPos, rockAbsPos)` path, and emit a `KindData.RockSolo` `CellEntry` per rock
into the union map (deduped/clamped/sorted normally). Add a rock-run-in-SENSOR-window test
(needs a grid with seeded rocks — the 16×16 perception-test grid has none today).

## TD-20.1-B — ADJACENCY-CARDINALITY test is weak on an empty neighbourhood

**Surfaced:** codex MEDIUM (round 2); kept as `<= 8` bound (correct) with a noted option.

**Finding:** `buildCellEntries` does not emit empty cells (`kind==null && envState==0`,
`TickBroadcaster:~492`). With the perception tests' mocked env returning 0, an empty
neighbourhood emits 0 entries, so the `cells().size() <= 8` assertion passes trivially
(0 <= 8) without proving the 8-ring shape.

**Why deferred:** The binding contract the test must pin is the `<= 8` UPPER bound (no 5×5
union leaked into a no-SENSOR LOCOMOTOR frame), which `<= 8` does correctly. Exact-8
cardinality is a nice-to-have, not the contract.

**Fix sketch:** Seed the 8 Moore-ring neighbours with a non-default kind/occupant so exactly
8 emit, and assert `== 8` alongside the `<= 8` bound.

## TD-20.1-C — REPRODUCER auto-place is never triggered for a passive bot (end-to-end gap)

**Surfaced:** codex (BLOCKER); adjudicated down after code verification.

**Finding:** D-02 delivered the server-side auto-place (`ActionResolver.resolveReproducerBud` +
`nearestFreeCell`) and its contract is correctly built and tested. BUT the trigger is
action-gated: Phase 3 of `resolveActions` only iterates composite members that submitted an
action (`ActionResolver.java:516-524`), and `HeuristicBrain.decide` returns `null` for every
composite role ≠ LOCOMOTOR (`HeuristicBrain.java:99-101`, "deferred post-MVP"). So a genuinely
passive REPRODUCER (the only kind the heuristic produces) never buds; the tests only pass because
they send explicit `R` actions.

**Why deferred:** Pre-existing — composite-member client brains (roles 1..5) were deferred
post-MVP before 20.1; D-06 explicitly scoped brain work to LOCOMOTOR only. 20.1's D-02 server
contract ("bot sends R, direction ignored, server auto-places") is delivered and tested; the
missing piece is the bot/server fallback that emits the trigger. Not a 20.1 regression.

**Fix sketch:** Either (a) add an authority-lite client brain that emits `R` for REPRODUCERs, or
(b) add a server-side per-tick fallback that runs `resolveReproducerBud` for each composite's
REPRODUCER when no action was queued (subject to the cooldown in TD-20.1-E).

## TD-20.1-D — stale LOCOMOTOR `V` ballot survives a same-tick last-write-wins overwrite

**Surfaced:** codex (HIGH); confirmed in code; pre-existing.

**Finding:** `queueAction` overwrites `pendingActions` last-write-wins (`ActionResolver.java:353`)
but the separate `pendingVoteBallots` entry set on a `V` (line 365) is never cleared. In
`resolveCompositeMovements` the ballot is read unconditionally first (line 975), with the
verb-`M`-arg fallback only used when the ballot is null. So a same-tick `V|888` then `M|6` from
one LOCOMOTOR session still votes with the stale `888`.

**Why deferred:** Pre-existing (the `pendingVoteBallots` machinery is from plan 15-06 / Phase 19.5,
untouched by 20.1). Near-zero live exploitability: the heuristic LOCOMOTOR emits exactly one `V`
per tick, so the double-submit precondition needs a custom/misbehaving client.

**Fix sketch (2-line):** In `queueAction`, when an overwrite replaces a prior action, clear the
session's `pendingVoteBallots` entry unless the new verb is also `V`; OR in
`resolveCompositeMovements`, gate the ballot read on the final action verb being `V`.

## TD-20.1-E — composite REPRODUCER has no replication cooldown

**Surfaced:** opencode (MEDIUM); pre-existing.

**Finding:** The solo-particle `resolveReproduce` checks `lastReproducedTick` against the
type-profile cooldown; the composite `resolveReproducerBud` path has no cooldown gate, so a
REPRODUCER could bud every tick while pool energy and a free cell exist.

**Why deferred:** Pre-existing (the old direction-based composite path also lacked a cooldown);
pool-energy drain + starvation floor are natural brakes; tied to TD-20.1-C (REPRODUCERs don't
fire live today anyway). Add the cooldown when the trigger lands.

## TD-20.1-F — SENSOR-distance threat avoidance (flee gate `maxDist=1`)

**Surfaced:** codex (BLOCKER); already a documented accepted TD from the 20.1-03 plan.

**Finding:** `HeuristicBrain` flee logic gates on `adjacent(predators, 1)`, so a predator visible
only via a SENSOR (Chebyshev dist ≥ 2) does not influence the LOCOMOTOR vote. The toward-food half
of D-06 (steer toward SENSOR-only food) IS delivered and now genuinely tested (`sensorFoodSteer`
fixed to dist-4). Only the away-from-SENSOR-distance-threat half is deferred.

**Why deferred:** Conscious MVP-scope decision, documented in the `decideLocomotor` Javadoc, the
`threatAvoid` test comment, and 20.1-03-SUMMARY. Not silently dropped.

**Fix sketch:** Extend the flee gate to rank away from predators at dist ≥ 2 when those cells come
from the SENSOR union (mirror the toward-food path's distance handling).

## TD-20.1-G — same-tick member-out / sibling-in roster race (pre-existing, LOW)

**Surfaced:** re-review adversarial verifier (LOW); pre-existing, not introduced by the B6 guard.

**Finding:** In `buildRosterIfChanged`, if a composite member vacates its registry-tracked cell
within a tick and a *sibling* of the same composite moves into that vacated cell, the new
cross-composite guard still passes (same `compositeId`) and the roster emits the wrong relative
coord — the cell that moved in, not the one that moved out. The B6 guard correctly handles the
*foreign*-occupant case; this same-composite-displacement edge is a stale-registry race that
predates the fix.

**Why deferred:** Pre-existing; narrow (requires two same-tick intra-composite moves into/out of
one cell); single-threaded tick ordering makes it rare. Fix belongs with a broader
registry/grid consistency pass, not this phase.
