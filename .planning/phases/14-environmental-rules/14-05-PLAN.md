## Revision Notes (reviews cycle 3)

This revision addresses the three cycle-3 Codex HIGH/MEDIUM/LOW items specific to 14-05.

**Core changes from cycle 2 plan:**

1. **Composite MOVEMENT_PLUS_1 redesigned to reuse the existing speed gate (Codex HIGH cycle 3).** The cycle-2 plan added `CompositeState.lastMovementTick` + `CompositeState.canMoveAtTick` + `CompositeConfig.moveCooldownTicks` — a PARALLEL cooldown system layered on top of the existing `ActionResolver.resolveCompositeMovements` speed gate at lines 743-771, which uses `compositeTicksSinceMove` + `moveInterval`. Codex flagged this double-gates unbuffed composites AND silently altered baseline composition-based speed.

   **Cycle-3 fix:** the NEW cooldown model is REMOVED entirely. MOVEMENT_PLUS_1 now operates on the EXISTING `moveInterval` calculation:

   ```java
   // EXISTING (unchanged for unbuffed):
   int locomotorCount = countLocomotors(composite);
   int colonySize = composite.getMemberCount();
   double speed = (double) locomotorCount / colonySize * compositeConfig.speedConstant();
   int moveInterval = speed >= 1.0 ? 1 : (int) Math.ceil(1.0 / speed);

   // NEW (Codex HIGH cycle 3 — minimal, single-source-of-truth buff):
   boolean anyLocomotorBuffed = hasAnyBuffedLocomotor(composite);   // scan members for MOVEMENT_PLUS_1
   int effectiveInterval = anyLocomotorBuffed
           ? Math.max(1, moveInterval - 1)
           : moveInterval;

   int ticksSince = compositeTicksSinceMove.getOrDefault(compositeId, effectiveInterval);
   if (ticksSince < effectiveInterval) {
       continue;
   }
   ```

   Unbuffed composites see the SAME `moveInterval` they see today. Buffed composites move at one tier faster (interval -1, floored at 1). No new fields, no new config, no parallel gating system. Baseline behavior is bit-for-bit identical to pre-Phase-14.

2. **`OVERCROWDED_THRESHOLD_DEFAULT = 6` (Codex MEDIUM cycle 3).** The cycle-2 plan set the constant to 5, but `SimulationConfig.defaults()` returns `overcrowdingThreshold = 6` (verified at `src/main/java/com/paralife/engine/SimulationConfig.java:36`) and `application.yml` specifies `overcrowding-threshold: 6` (verified at `src/main/resources/application.yml:33`). The constant MUST match the shipped default. Test fixtures continue to read `SimulationConfig.defaults().overcrowdingThreshold()` dynamically, so this is belt-and-braces.

3. **`CellView.flags` vs `CellView.cellStatus` documentation (Codex LOW cycle 3).** A dedicated Javadoc block is added to `Messages.CellView` explaining the distinction:
   - `flags`: server-authoritative GLOBAL state. Bits set by SimulationEngine (e.g. `FLAG_OVERCROWDED` after `processOvercrowding` uses the full Moore-8 neighborhood).
   - `cellStatus`: vision-scoped CLIENT-PERSPECTIVE state. Bits recomputed per bot using only cells inside the bot's vision range. At vision edges, bits may differ from `flags` because out-of-vision neighbors are unknown to the bot.
   Future bot developers reading perception payloads MUST NOT conflate the two. This is documented once in code — the single location new bot developers will encounter when inspecting the CellView type.

All other cycle-2 fixes (HeuristicBrain observable-only, BotClient untouched, ATTACK_PLUS_1 enumeration, UPKEEP_MINUS_1 via per-member passiveDrain) are preserved unchanged.

 * A single cell in a perception payload.

 * <p><b>{@link #flags} vs {@link #cellStatus} (Codex LOW cycle 3):</b>
