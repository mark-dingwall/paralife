    **Tiebreaker rationale (D-04 amendment, B2.1 final shape):** the simulation CAN produce two pending grants for the same entityId in one tick (e.g., simultaneous mutagen + cure side-effects targeting the same entity). Sorting by entityId alone leaves the tie's order CHM-dependent → non-deterministic RNG consumption. The invariant: the comparator must produce a total order over any plausible same-entity multi-grant tick.

    **C2.2 — comparator-totality justification.** The 4-key cascade `(entityId, initialTicks, position.x, position.y)` is a TOTAL order over `PendingGrant` IFF no two `PendingGrant` instances share all four field values within a single tick. Source-of-truth invariant: a `PendingGrant` is constructed at most once per `(entity, buff-source-event, tick)` tuple — duplicate grants for the same entity in the same tick must come from distinct buff-source events (mutagen vs cure vs lightning), and those events occupy distinct `position` cells (mutagen at the entity's cell vs cure at a different cell, etc.) OR distinct `initialTicks` durations. The cascade exhausts the discriminating axes; a residual collision would require two distinct buff sources at the same cell with the same duration targeting the same entity in the same tick — physically impossible given the CA's per-tick spawn budget at any one cell. If the source-event-id invariant is later weakened, append `.thenComparing(g -> g.sourceEventId())` (or whatever monotonic source-event sequence exists). Do NOT use `System::identityHashCode` — it varies across JVM runs and would re-introduce the determinism bug. If no monotonic source-event field exists, the invariant becomes load-bearing — require an ADR before adding any buff source that violates it. No test change needed for C2.2 — the rationale is documented to prevent future drift.
