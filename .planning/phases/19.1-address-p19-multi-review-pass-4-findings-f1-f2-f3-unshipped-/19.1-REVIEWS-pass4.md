# Cross-AI Plan Review — Phase 19.1 (Pass 4)

## Gemini Review

### 1. Summary
The implementation plans for Phase 19.1 are exceptionally thorough, well-reasoned, and tightly constrained. The strategic decision to sequence these regression and technical debt fixes prior to scaling the architecture in Phase 20 is sound. The plans exhibit a high degree of defensive engineering, correctly leveraging exact-match analogs from existing codebase patterns and strictly enforcing contracts with comprehensive test coverage. While the overall structure is excellent, a few minor compiler and type-safety oversights in the test pseudo-code could cause friction during the execution phase.

### 2. Strengths
- **Strict Analog Adherence:** Every task points to an exact or sibling analog in the current source code, drastically reducing the cognitive overhead and error surface for implementers.
- **Defensive Contract Pinning:** Promoting structural fixes (e.g., `Event.ALL_CODES` as the single source of truth) and adding `ActionResolverDrainSemanticsTest` to enforce the deferred-not-lost semantic ensures that future refactors cannot silently regress these subtle behaviors.
- **Deterministic Test Coverage:** The rigorous updates to `EnvironmentDeterminismTest` and the introduction of `GoldenTraceWithActionsTest` eliminate RNG-based flakiness and establish reliable regression baselines before Phase 20.
- **Concurrency Primitives:** The resolution of the `markStalled` deadlock gracefully handles the Jetty `sendMessage` blocking behavior using targeted `CloseStatus` signals rather than heavy-handed threading workarounds.
- **Comprehensive TDD Guidance:** Test descriptions meticulously specify setup, execution boundaries, and explicit assertions (e.g., cross-thread latching in `MarkStalledTickBoundIntegrationTest`).

### 3. Concerns
- **HIGH — Compiler Error in `markStalled` Test:** In **Plan 03, Task 03c**, the pseudo-code for testing the `markStalled` deadlock invokes `handler.markStalled(fake, "stuck-VT-test");`. However, the method signature in `WorldWebSocketHandler.java` is `public void markStalled(WebSocketSession session, long stallTick)`. Passing a `String` as the second argument instead of a `long` will fail compilation.
- **MEDIUM — Missing Type Qualifiers:** In **Plan 05, Task 05c**, the `DrainObserverForD20Pin` interface specifies `Map<String, ActionFrame> snapshot`. `ActionFrame` is an inner record of `Frame`. Unless `com.paralife.codec.Frame.ActionFrame` is explicitly imported (or referenced as `Frame.ActionFrame`), the compiler will throw an unresolved symbol error.
- **LOW — CI Execution Jitter in Tick Bound Test:** In **Plan 03, Task 03c**, the dynamically calibrated bound uses `baselineMaxMs * 5 + 20ms`. Under highly starved CI runner environments, baseline execution could spike unnaturally, potentially masking real regressions, or conversely, jitter during the stalled phase could exceed 20ms and induce flakiness.

### 4. Suggestions
- **Fix the `markStalled` Test Call:** Update the `markStalled` execution in `MarkStalledTickBoundIntegrationTest` (Plan 03, Task 03c) to pass a valid tick number, e.g., `handler.markStalled(fake, 3L);`.
- **Explicit Imports for Test Seams:** In Plan 05 Task 05c, explicitly define the seam map as `Map<String, Frame.ActionFrame>` rather than `Map<String, ActionFrame>` to prevent compilation drift.
- **Refine `buildMinimalEventFrame` Logic:** In Plan 01 Task 01d, ensure the pseudo-code explicitly notes that `'B'` must be caught in the `!needsMagnitude` branch.
- **Document Event Publisher Threading:** In tests utilizing `applicationEventPublisher.publishEvent(...)`, include a brief inline comment emphasizing that this execution will block the test thread until the `SimpleApplicationEventMulticaster` has completed its synchronous dispatch.

### 5. Risk Assessment
**Overall Risk: LOW**
The operational risk of implementing these plans is exceptionally low. Scope boundaries rigorously defined, all changes directly address verifiable pre-existing flaws using established in-tree patterns. Correcting the minor compiler mismatches highlighted above will yield a smooth execution phase.

### Concerns

#### HIGH

- **Plan 02, falsifier wording (C2.3 amendment is logically backwards).**
  Falsifier reads: *"Same-seed `ToxinPathGenerator.generatePath(w, h, 0xDEADBEEFL)` produces byte-identical `List<Position>` across two calls"* — but byte-identical IS the desired determinism outcome, not a falsifier. - **Plan 03 D-14 (detach-timeout metric) ships without behavioral test.**

  **Fix:** Add a `@Test` to `OutboundSenderTest` that drives a deliberately-uninterruptible drain VT, calls `detachSession(String)`, and asserts the counter increments.

- **Plan 01 Task 01b, F1 test scope risk.**
  Test publishes `TickEvent` and asserts `botRegistry.drainDeaths().isEmpty()`. But `TickEvent` runs the entire `@EventListener` chain. If a future change adds a death-queueing path on the same tick, the test false-positives.
  **Fix:** Tighten Test 1 to assert "post-tick `drainDeaths()` size equals known-good count" rather than `isEmpty()`.

- **Plan 02 D-04 totality argument relies on cure-event invariant not stated in code.**
  C2.2 argues `(entityId, initialTicks, position.x, position.y)` is total iff "two distinct buff sources at the same cell with same duration targeting the same entity in the same tick are physically impossible." Cure events are NOT CA-budgeted.
  **Fix:** Either (a) add a `sourceEventId` field to `PendingGrant` and append `.thenComparing(g -> g.sourceEventId())`, OR (b) write the load-bearing-invariant ADR now and link from the comparator comment.

#### LOW

- **Plan 01 Task 01d `buildMinimalEventFrame` helper, vectors() row availability.** No `<read_first>` validates the row inventory.
- **Plan 03 BlockingFakeSession implementation completeness.** `WebSocketSession` has ~16 methods; plan stubs only the relevant ones. Spring/Jetty might call e.g. `getRemoteAddress()` during attach/close, NPE-ing the test.
- **Plan 04 cleanup* test, production-path coverage.** If production has a third disconnect path that bypasses both, BL fix is partial.
- **Plan 05 Task 05d line 187 (PerceptionBroadcaster UNKNOWN tech-debt row).** "Drop the row" instruction is heavier-handed than "mark resolved with date".
- **Plan 05 LM (D-12) and DR-pin (D-20) are pin tests, not red-green TDD.** Both pass against pre-fix tree; they catch FUTURE regressions. Plan acceptance language treats them as bug-fix tests. Minor framing issue.

### Suggestions
1. **Run a pre-execute consistency pass.** Before `/gsd-execute-phase 19.1`, run a single grep verifying the C2.3 falsifier wording and the C5.5 floor are landed correctly.
2. **Add SUMMARY templates.** Surface decisions about cure-event invariant, processedCountForVerb helper, vectors() row inventory.
3. **Consider a Plan 05 split.** Plan 05 is now 6 tasks across 7 D-IDs. If any single task flakes, the whole wave-4 commit gets blocked.

## Codex Review

### Summary
The plans are unusually thorough and the amendment trail shows real convergence: most earlier factual drift has been corrected, especially around `ToxinPathGenerator`, `tickOnce`, `entitySnapshot`, and `markStalled`. I would approve the overall structure, but not execute unchanged. Pass 4 still has several high-risk test/verification issues where the plan may either fail during implementation or, worse, pass while not pinning the intended behavior.

### Strengths
- Clear phase boundary: bug-fix hardening kept separate from P20 multiplexing.
- Good pairing of spot fixes with regression tests, especially F1/F2/F3 and the deterministic RNG work.
- Amendments substantially improved factual accuracy: static toxin generator, session-id `queueAction`, no fake `tickOnce`, correct `entitySnapshot` count.
- The `markStalled` direction is technically sound: close transport first, accept OOB 408 as best-effort, preserve `SERVICE_RESTARTED`.
- Conservative dependency ordering reduces merge risk across overlapping files.

### Concerns

- **HIGH — Plan 05d / OD verification command is wrong for real `@Order` usage.**
  The plan's set-equality command greps only numeric annotations: `@Order\([0-9]+\)`. Local source includes `@Order(TICK_ORDER)` and `@Order(Integer.MAX_VALUE)`, while CLAUDE.md is expected to mention `@Order(14)`, `@Order(25)`, and `@Order(MAX_VALUE)`. Verification will either fail incorrectly or fail to verify the intended mapping. Use a small source-aware table check or explicitly grep the concrete classes and constants.

- **HIGH — Plan 05c / DR-pin seam does not match current `ActionResolver.drainActions`.**
  Current code has no snapshot phase; it iterates `pendingActions.entrySet()` and calls `pendingActions.remove(e.getKey(), e.getValue())` per entry. The proposed observer "after snapshot before remove" implies either a behavior-changing refactor or an underspecified hook point. The seam should be placed precisely after `var e = it.next()` for the targeted session and before that entry's `remove(k,v)`, or the test should explicitly refactor to a copied snapshot and prove semantics are unchanged.

- **HIGH — Plan 05a / GoldenTraceWithActions processed-action gate is underdefined and likely flaky.**
  "Count observable footprint per verb in captured frames" is not a concrete mechanism. Many queued actions can legitimately have no visible effect: `E` with no consumable target, `R` without valid energy/target, `V` without quorum relevance, deaths/formations changing live count. Also `totalQueued = BOT_COUNT * TICK_COUNT` is wrong if the loop queues over `liveEntityRegistry.snapshot()`. Track actual queued count per verb and add resolver-side processed counters or deterministic fixtures where each verb is guaranteed valid.

- **HIGH — Plan 02a / pending-grants comparator may still preserve nondeterminism on ties.**
  Sorting by `(entityId, initialTicks, position.x, position.y)` only fixes determinism if those fields are unique for every pending grant. If two grants collide under that comparator, Java's stable sort preserves the original `ConcurrentHashMap` iteration order, which is the nondeterministic input. Either enforce/verify uniqueness in code, collapse duplicates deterministically, or add a deterministic monotonic source sequence to `PendingGrant`.

- **MEDIUM — Plan 03c / VT-exit assertion can false-green.**
  Checking `senderThread(id) == null || !t.isAlive()` after detach is insufficient because `detachSession` removes the map entry before the VT necessarily exits. Capture the `Thread` before invoking `markStalled`, then assert `join` and `!isAlive` on that captured reference.

- **MEDIUM — Plan 03a / detach-timeout metric lacks a concrete failing test.**
  The plan adds the counter and says to test it, but the action does not define a deterministic timeout scenario. Add a fake sender thread/session path that guarantees `detachSession(String)` join timeout, then assert the meter count increments.

- **MEDIUM — Plan 04c / FLEEING transfer is grep-only.**
  Auto-expiry is not a reason to skip a behavioral test. This can be tested immediately after formation/dissolve in a single tick. A grep count will not catch reversed arguments or wrong member mapping.

- **MEDIUM — Plan 01d / reverse-drift gate calls a private method.**
  `PerceptionCodec.validateEventCode` is private in the plan context. The reverse-drift test cannot directly iterate 0..127 against it unless visibility changes or reflection is used. Prefer a public decode-based helper that builds valid magnitude/no-magnitude frames per code, or make a deliberate package-private seam.

- **LOW — Plan 04b / cleanupByEntityId metric side effects need explicit caller expectations.**
  The hard-stop audit is good, but the plan should also name expected metric side effects after moving env cleanup before the `sessionId == null` branch. Otherwise tests may bless cleanup behavior while terminal-dropout/active/stalled counters drift.

### Suggestions
- Replace text-grep verification for complex contracts with small focused tests or scripts that parse the relevant source shape.
- For all deterministic-order fixes, assert comparator uniqueness or add a deterministic tiebreaker that is part of the data model.
- Make the ActionResolver seam narrowly scoped to one key and one hook invocation; avoid a general observer that can fire repeatedly or alter drain ordering.
- Change GoldenTraceWithActions from "random-ish valid actions" to a staged fixture: one guaranteed-valid movement, consume, reproduction, and vote path per cycle, then digest the result.
- Add immediate FLEEING transfer tests for composite formation and dissolve; these are cheap and reduce reliance on grep acceptance.

### Risk Assessment
Overall risk: **MEDIUM**, with a few **HIGH** execution hotspots. The implementation direction is sound, but Plans 02 and 05 still contain verification designs that may be nondeterministic or false-green. Fix those before execution; otherwise the phase can ship with tests that look strong but do not actually pin the intended contracts.
