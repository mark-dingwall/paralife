## Gemini Review
Here is the pass-5 review of the Phase 19.1 implementation plans. 

### Summary
The pass-4 amendments successfully resolve the majority of the factual drift, correcting pseudo-code signatures, ensuring proper test coordination, and pinning unambiguous contracts for the `ToxinPathGenerator` and `ActionResolver`. The implementation structure across Plans 01–05 is largely executable and effectively uses exact-match analogs. However, two significant risks remain: a severe thread-safety violation introduced by the new lifecycle cleanup logic in Plan 04, and a mathematically unachievable verification floor in the `GoldenTraceWithActionsTest` in Plan 05 that will cause immediate CI failure.

### Plan 04 — Lifecycle leaks
- **Strengths**:
  - FLEEING state transfers seamlessly at composite formation and dissolution boundaries.
  - `AdmissionMetrics` tag migration correctly pairs with `ResumeTokenRegistry` remapping.
- **Concerns**:
  - **HIGH** - **Thread-safety violation in `cleanupBot`.** `cleanupBot` is invoked from the Jetty WebSocket I/O thread (via `afterConnectionClosed`). Plan 04 introduces direct mutations to physics engine state (`buffRegistry.unregisterEntity`, `hooks.clearInfectionOnDeath`, `environmentEngine.fleeingRemove`) from this I/O thread. The architectural convention dictates a "Single-threaded simulation core." Unless these specific registries are backed by concurrent collections (which physics engines rarely use for performance), this will cause `ConcurrentModificationException`s or state corruption when the tick thread reads/writes them simultaneously.
- **Suggestions**:
  - Do not mutate simulation engine state directly from `cleanupBot`. Instead, have `cleanupBot` enqueue the disconnected `entityId` into a concurrent collection (e.g., `ConcurrentLinkedQueue<String> pendingDisconnects`). A tick-pipeline component (or `DeathFinalizer`) should drain this queue and execute the env-state cleanup safely on the tick thread.
- **Risk Assessment**: HIGH. Introduces unsafe cross-thread mutations into the single-threaded physics core.

---

### Plan 05 — Regression coverage + polish
- **Strengths**:
  - Consolidates test coverage efficiently, preventing test-suite fragmentation.
  - `ActionResolverDrainSemanticsTest` locks in the deferred-not-lost contract unambiguously using the `AtomicReference` capture seam.
  - `CLAUDE.md` and Javadoc updates resolve stale documentation gracefully.
- **Concerns**:
  - **HIGH** - **Mathematically unachievable 90% floor in `GoldenTraceWithActionsTest`.** The test cycles `M`, `E`, `R`, `V` verbs evenly across the population. The `E` (Eat) and `R` (Reproduce) actions have a very high legitimate failure rate in deterministic scenarios (e.g., trying to eat where there is no nutrient, or reproducing into an occupied cell). Because the test iterates indiscriminately, the success rate for `E` and `R` will drag the aggregate processed count far below the 90% floor (e.g., ~60-70% total), causing reliable CI failures. The E5.3 amendment fixed the denominator but ignored the natural rejection rate of the verbs themselves.
  - **MEDIUM** - **Missing test registration setup.** Task 05c pseudo-code initializes `String sessionId = "S1"` but omits the `botRegistry.register(...)` step that amendment E5.1 mandates. If an implementer copies the code directly, the test will fail setup.
- **Suggestions**:
  - **Fix the 90% floor:** Do not use a single aggregate 90% floor for all verbs. Instead, assert that `M` and `V` (which rarely fail) meet the 90% floor, while enforcing only a `> 0` or nominal floor for `E` and `R`. Alternatively, replace the indiscriminate verb cycle with a staged fixture that guarantees valid conditions for each verb.
  - **Update Task 05c pseudo-code:** Explicitly insert `botRegistry.register("S1", "E1", new Position(0, 0))` in the `ActionResolverDrainSemanticsTest` skeleton to prevent implementer error.
- **Risk Assessment**: HIGH. The test design in its current form guarantees build failure.

---

### Cross-plan synthesis
The structural decisions across the 5 plans are sound, but the execution phase is endangered by two critical flaws. The thread-safety violation in Plan 04 threatens the stability of the simulation core under load by breaking the I/O vs. Tick thread boundary. Meanwhile, the `GoldenTraceWithActionsTest` in Plan 05 suffers from an uncalibrated success floor that ignores the natural rejection rate of the physics engine. Addressing these two specific HIGH risks will yield a highly robust Phase 19.1 deployment.

## Plan 02 — Determinism hardening

### Summary
Plan 02 closes F4 / CE / TX with the snapshot-and-sort and stateless-static-generator templates. Pass-4 amendments E2.1 (corrected falsifier wording — C2.3 had the inversion that would have made a passing TX test fail the gate) and E2.3 (non-applicability note: cures don't flow through `pendingGrants`) are correct as far as they go, but they leave the central comparator-totality concern uncovered: pass-4 reviewers (Codex HIGH, Claude MEDIUM) flagged tie-collisions falling back to `ConcurrentHashMap` insertion order via Java's stable sort, and the response was an argument for impossibility rather than enforcement in code.

### Strengths
- B2.1 4-key cascade `(entityId, initialTicks, position.x, position.y)` is correct in all branches the plan actually verifies. Source-of-truth invariant is well-stated.
- C2.1 fully-static `ToxinPathGenerator` (no ctor at all) is the cleanest end-state for stateless RNG. Removes both `final`-field tension and instance-state ambiguity.
- D3-T1 stale lowercase callsites scrubbed — no residual `toxinPathGenerator.generatePath` in acceptance.
- D3-M3 corrected the `identityHashCode` fallback in C2.2 before it shipped — that fallback would have re-introduced the bug it was meant to catch.
- E2.3 cure-events non-applicability note correctly bounds the comparator-totality argument to the actual data path (`scheduleBuffGrant` / siblings, not cures).

### Concerns

#### HIGH
- **Comparator tie-totality is documented, not enforced.** B2.1's totality claim depends on a `PendingGrant` ctor invariant that exists in narrative ("at most one per `(entity, buff-source-event, tick)`") but not in code. C2.2 documents the rationale; D3-M3 says fallback is `.thenComparing(g -> g.sourceEventId())` *if* a `sourceEventId` field exists, else "ADR required". E2.3 narrows scope to non-cure paths but doesn't add the discriminator. If two CA-budgeted buff spawns ever produce same-entity-same-cell-same-duration grants in one tick (e.g., overlapping toxin path + lightning?), the sort falls back to CHM order — the determinism bug returns silently. Java's `sort` is stable; insertion-order = CHM-iteration-order = nondeterministic.
  - **Where:** Plan 02 Task 02a action paragraph and acceptance.
  - **Suggestion:** Either (a) add `long sourceEventId` (or monotonic source-sequence) to `PendingGrant` now, append `.thenComparingLong(PendingGrant::sourceEventId)` to the cascade, and skip the ADR; or (b) write the load-bearing-invariant ADR in this phase and link from the comparator comment so it's surfaced at next review.

#### MEDIUM
- **Plan 02d multi-cure fixture validates only the *current* invariant.** The new `multiCureSameSeedDeterminism` test seeds same-tick multi-cure entities with distinct `(entityId, initialTicks)` — it cannot exercise the tie-collision path because the comparator isn't keyed on something that ties. So the test passes with or without the residual concern above. Pass-4 dismissed Codex's tie-collision flag in part because the test would catch any regression — but the test cannot.
  - **Where:** Task 02d acceptance.
  - **Suggestion:** Add one fixture row that *intentionally* produces two grants identical on all 4 cascade keys. If totality holds, this fixture cannot be constructed (good — promote impossibility from comment to test). If it can be constructed, the test fails until `sourceEventId` lands.

- **C2.1 caller migration list is partial.** Lists `EnvironmentEngine.java:405,1615`, `LightningTest.java:78`, `ToxinPathGeneratorTest.java:41,42,53,61,75`. If any other in-tree caller exists (e.g., a test fixture builder or a future P19.5 callsite I can't see), the migration breaks compilation. No `<read_first>` directive enumerates callers via `grep -rn "new ToxinPathGenerator"`.
  - **Where:** C2.1 amendment.
  - **Suggestion:** Add to Task 02c `<read_first>`: `grep -rn 'new ToxinPathGenerator\|toxinPathGenerator\.generatePath' src/{main,test}` — record output in SUMMARY.

#### LOW
- **CE inner-shuffle dismissal (A2.3) is correct but undertested.** A2.3 says `CompositeRegistry.memberIds` is `CopyOnWriteArrayList` so inner shuffle order is deterministic given a stable outer iteration. The relocated `CompositeEnergyDistributorDeterminismTest` (B2.4) would catch a regression on the OUTER iteration but not on the inner shuffle if `memberIds` is ever swapped to a `Set` or CHM-backed collection. Acceptable as a future-self note; not blocking.

### Suggestions
- Resolve the totality issue with a small data-model change (`sourceEventId`) rather than an ADR. Three lines in `PendingGrant` + one `.thenComparingLong(...)` is cheaper than the ADR overhead and gives the property "tests would fail if invariant breaks" instead of "comments will alert future reviewers."
- Make Task 02d's tie-totality aspirational fixture explicit so the impossibility argument is exercised.
- Pre-flight grep for residual `new ToxinPathGenerator` callers — cheap insurance for C2.1.

### Risk Assessment
**MEDIUM.** Determinism is the gate Plan 05's golden-trace baseline relies on. If the residual tie-totality concern materializes after Plan 05's baseline is pinned, the GoldenTraceWithActionsTest digest will flake under load and the implementer will chase a phantom CI bug. Cheap fix; worth landing.

## Plan 03 — Backpressure correctness

### Summary
Plan 03 lands the markStalled close-aware detach (HIGH MS), the EL VT-exit assertion, and the L1 detach-timeout metric. Pass-4 added the most amendments here: E3.1 fixed the `markStalled(fake, "stuck-VT-test")` compile error to `3L`; E3.2 added a behavioural counter test (`detachTimeoutIncrementsCounter`) that prevents the L1 metric from being silently regressed; E3.3 captures the `Thread` reference *before* detach so the post-detach assertion isn't reading a `null` map entry; E3.4 cited the `isOpen()` guard in CLAUDE.md so readers understand the OOB call is structurally short-circuited, not just exception-swallowed. The plan is now internally consistent and the markStalled deadlock is the right shape.

### Strengths
- D-07 close-status overload (`detachSession(WebSocketSession, CloseStatus)`) is the cleanest API: existing callers continue with `GOING_AWAY` default; markStalled requests `SERVICE_RESTARTED`. No redundant trailing `session.close`.
- E3.2 closes a real gap — declaration-only acceptance would let a future regression silently remove the increment.
- E3.4 tightens the CLAUDE.md narrative: the `isOpen()` guard at line 923 means OOB is structurally short-circuited post-close, not merely exception-swallowed. Important for future readers reasoning about close ordering.
- B3.4 paired-latch coordination (`markStalledStarted`/`markStalledFinished`) is the right discipline for cross-thread timing tests; eliminates `Thread.sleep` race.
- C3.1 pre-decided the fake-session injection seam (`OutboundSender.attachSession(WebSocketSession, int)` at :117) so the plan ships with no `human_needed` hold.

### Concerns

#### MEDIUM
- **`BlockingFakeSession` is sketched, not specified.** C3.1 gives a working skeleton: `sendMessage` awaits `closeLatch`, `close` counts down. But `WebSocketSession` is a 16-method interface (`getRemoteAddress`, `getAcceptedProtocol`, `getExtensions`, `getPrincipal`, `getBinaryMessageSizeLimit`, `setTextMessageSizeLimit`, `getUri`, `getHandshakeHeaders`, ...). If Spring/Jetty calls any of these during `attachSession` or `markStalled` (e.g., logging the remote address on failure), the test NPEs and the regression intent is lost.
  - **Where:** Task 03c action paragraph (BlockingFakeSession sketch).
  - **Suggestion:** Either (a) extend `org.springframework.web.socket.handler.AbstractWebSocketSession` if available, (b) sub-class `org.springframework.web.socket.adapter.NativeWebSocketSession` mock from spring-test, or (c) explicitly stub all 16 methods returning safe defaults. The plan should pin one path; "no-op stubs for the remaining" leaves it to interpretation.

- **20ms calibration floor may flake under heavy CI parallelism (OpenCode pass-4 LOW, not amended).** C3.3 documents the regime (`baselineMaxMs == 0` → 20ms floor catches order-of-magnitude deadlocks). Under WSL2 / CI runners with VT-carrier contention, baseline can spike to 30–50ms transiently and the bound becomes `30 * 5 + 20 = 170ms`, which masks a 100ms regression. Conversely, if the deadlock test is run in isolation on a fast runner, baseline = 0 and the 20ms floor is correct. The bound is double-edged.
  - **Where:** Task 03c calibration paragraph.
  - **Suggestion:** Add a hard cap (`Math.min(bound, 200ms)`) so the multiplier can't make the bound useless on a slow baseline. Alternative: instrument the test to log `(baseline, observed, bound)` and fail with the triple in the assertion message — already partially done; just ensure it always fires regardless of pass/fail so flake triage has data.

#### LOW
- **E3.1 is correct but the literal `3L` assumes the test publishes ticks ≥ 3.** If the test only drives 10 baseline ticks then injects markStalled "around tick 3", `markStalled(fake, 3L)` correctly mirrors the tick the stall is associated with. But the literal is opaque; future readers may wonder why `3L`. Add a `// stallTick: matches the tick at which the stuck VT was injected` comment.

- **L1 metric increment site.** Step 3 places `metrics.incDetachTimeout()` *before* the warn log so it fires even if log filtering hides the warn. Good. But the increment fires on *every* detach timeout, regardless of cause (interrupt-deaf vs slow-but-eventual). Operators reading the counter see "detach failures" without distinguishing. Acceptable for now; flag for SLO definition in Phase 21.

### Suggestions
- Pin the `BlockingFakeSession` parent class or interface inheritance source. Don't leave it to executor guesswork — it's a compile/test surface, not a design choice.
- Add a hard cap on the calibrated bound so the multiplier doesn't make it toothless.
- Annotate the `3L` literal in the markStalled call.

### Risk Assessment
**LOW–MEDIUM.** The deadlock fix itself is well-designed. Residual risks are test-fixture sketches and CI-jitter calibration — both fixable inline at execute time without re-planning. The MEDIUM rests on the `BlockingFakeSession` ambiguity, which has a real chance of producing a flaky or NPE-ing test on first run.

### Strengths

- E5.2 hook-point clarification ("inside the per-entry iteration loop, after `it.next()` and before `remove(k,v)`") closes Codex's "underspecified hook" concern. The seam is one null-checked line, not a snapshot-phase refactor.
- C5.5 two-part gate (per-verb ≥ 1 AND aggregate 90%) is well-structured. The per-verb floor catches "M is the only verb the parser accepts" silently-broken state.
- D-11 GoldenTraceWithActionsTest has the right shape: cycle M/E/R/V across ticks, drive deterministic verbs, pin a separate baseline. B5.4 baseline-commit gate (no `_seed_marker: PLACEHOLDER` in committed JSON) prevents zero-content baselines.

- C5.1 corrected `entitySnapshot()` count to 3 (codex pass-4 was right; earlier "verified 2" was wrong). Pre-/post-edit awk gates verify the count delta.
- D3-T4 helper-body pinning (`numpadDir`, `numpadBallot`) closed the two-implementers-two-fixtures risk.

### Concerns

#### HIGH
- **"Processed" remains undefined for the 90% gate (Codex pass-4 HIGH, partially addressed).** E5.3 fixed the denominator but did not define the numerator. The plan says "count its processed/observable footprint in the captured frame stream" — this is hand-waved. What is a `V` action's observable footprint? If V (vote) requires quorum and the deterministic fixture has no quorum, V is queued, drained, processed, and produces no frame. Does that count toward "processed"? If yes, how does the test count it without an `ActionResolver.processedCountForVerb(c)` accessor (which the plan doesn't add)?
