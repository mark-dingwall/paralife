### F6 — Codex REF: `previousPoolEnergy` stale entry on panic-dissolve

- **Reviewer/severity:** codex REF only / not graded but framed as a follow-up.
- **Citation:** `SimulationEngine.java:1138-1156`.
- **Verdict:** **VALID, severity LOW (memory leak, not correctness).**
- **Evidence:** lines 1138-1142 fill `currentPoolEnergies` with all composites *before* `checkPanicZone`. If panic-zone dissolves composite X, line 1151 (`previousPoolEnergy.putAll(currentPoolEnergies)`) re-adds X to the per-tick map even though X no longer exists in the registry. Next tick's `processDeaths` won't see X in `compositeRegistry.getAll()` so the entry sits orphaned until a same-ID composite is created (impossible — IDs are monotonic `composite-N`). Bounded leak: one entry per ever-dissolved composite over process lifetime.
- **Severity check:** unbounded `Map<String,Integer>` growth ≈ 8-byte string ID + 4-byte int ≈ <50 bytes/entry; even at 1k dissolves/hour the heap impact is sub-MB/day. LOW.
- **Action — OPTIONAL:** add a single-line filter in the loop that builds `currentPoolEnergies` *or* (better) move `currentPoolEnergies` build to *after* `checkPanicZone` so dissolved composites are naturally excluded. Defer to Phase 21 if cleaning F4/F5 separately.
