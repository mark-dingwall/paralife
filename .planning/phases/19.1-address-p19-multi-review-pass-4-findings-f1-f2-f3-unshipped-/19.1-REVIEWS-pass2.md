## Overall Assessment

The Phase 19.1 plans are highly concrete, meticulously scoped, and structurally sound. The integration of the B-amendments effectively closed the executable gaps from pass-1, transforming pseudo-code heuristics into enforceable, compile-ready contracts. Moving the `Event.ALL_CODES` to a single source of truth, adopting a stateless `ToxinPathGenerator`, using cross-thread `CountDownLatch` coordination, and dropping the flaky stress-test fallback significantly de-risk the phase. The remaining risks are localized to CI pipeline jitter and subtle lifecycle cleanup dependencies.

Overall Risk Level: **LOW-MEDIUM**

### Plan 19.1-01: Unshipped fix verification & landing

**Summary**
This plan accurately addresses the F1, F2, and F3 deployment gaps. The promotion of D-15 (codec convention gate) into this plan pairs the symptom fix (F2) with its structural cure (`Event.ALL_CODES`), preventing the dual-list trap from ever recurring. The B-amendments successfully refined the F1 test mode and locked down array mutability.

**Strengths**
- Changing `Event.ALL_CODES` from `char[]` to `String` eliminates the risk of external array mutation disrupting the codec gate.
- Using `ApplicationEventPublisher` for the F1 test accurately simulates the composite formation without requiring visibility hacks or reflection to test `updateBotRegistryForFormation`.
- Utilizing `PerceptionCodecErrorTest` avoids generating synthetic test files and respects the existing test architecture.

**Concerns**
- **LOW:** The F1 test relies on `ApplicationEventPublisher` to trigger the composite formation. If the `TickEvent` triggers other unrelated event listeners, it could mutate state and cause test flakiness, particularly around `BotRegistry.drainDeaths()`.

**Suggestions**
- In the F1 test, ensure the `TickEvent` payload or the mocked context is sufficiently narrow so that only the composite formation logic reacts to it, preventing other `@EventListener`s from polluting the queue.

**Risk Assessment: LOW**
The edits are tightly bound to pinned lines and the B-amendments successfully resolved the test visibility and mutability concerns.

### Plan 19.1-03: Backpressure correctness

**Summary**
This plan resolves the `markStalled` deadlock using a close-aware `detachSession` overload. The B-amendments dramatically improved the `MarkStalledTickBoundIntegrationTest` by introducing `CountDownLatch` coordination and a dynamic, CI-tolerant performance bound.

**Strengths**
- Using `CountDownLatch` (`markStalledStarted`, `markStalledFinished`) guarantees the thread interleaving is perfectly synchronized, avoiding flaky `Thread.sleep` races.
- The calibrated performance bound (`baselineMaxMs * 5 + 20ms`) is excellent. It establishes a dynamic threshold that prevents CI jitter from failing the test while still catching order-of-magnitude deadlocks.
- Capturing the thread reference *before* invoking `detachSession` correctly avoids a `NullPointerException` on the subsequent `t.isAlive()` check.

**Concerns**
- **MEDIUM:** The test relies on `applicationEventPublisher.publishEvent(new TickEvent(i + 1))` to simulate the tick loop. If the Spring context processes these events asynchronously or defers them under load, the baseline service-time measurement will be artificially low.
- **LOW:** `sendOutOfBand` catches `IllegalStateException`, which is appropriate, but network implementations may sometimes wrap closure exceptions in generic `RuntimeException`s.

**Suggestions**
- Ensure the `ApplicationEventPublisher` utilized in the test context is explicitly bound to a `SimpleApplicationEventMulticaster` with no `TaskExecutor` configured, guaranteeing synchronous execution for the baseline calculation.

**Risk Assessment: LOW-MEDIUM**
The `CountDownLatch` and dynamic bound additions resolved the major CI and race condition risks.

### Plan 19.1-04: Lifecycle leaks

**Summary**
Plan 04 handles cleanup memory leaks gracefully. The removal of the heavy `git worktree` workflow in favor of an `@Disabled` state-flip test is a massive CI win. The A4.3 placement shift handles entityId-only code paths perfectly.

**Strengths**
- The `@Disabled("baseline")` approach provides the exact same TDD validation as the git worktree strategy without the I/O and CI teardown overhead.
- Relocating the environment cleanup *before* the `sessionId == null` early return in `cleanupByEntityId` correctly covers admission aborts and post-`markDead` sweeps.
- `clearInfectionOnDeath` purity was successfully verified, confirming that direct invocation is safe.

**Concerns**
- **MEDIUM:** By placing the env-cleanup before the `sessionId == null` check, `cleanupByEntityId` will wipe `buffRegistry` and `fleeing` state for any disconnected entity. If an entity is currently in the `markStalled` "grace window" awaiting reconnect, invoking `cleanupByEntityId` will incorrectly wipe its environmental state. The plan requires the executor to `grep` for callers, but this is a manual check.

**Suggestions**
- Add a specific test case that simulates a `markStalled` disconnection followed by a grace-window reconnect, explicitly asserting that the entity's buffs and fleeing state were *not* wiped during the stall period.

**Risk Assessment: MEDIUM**
The early-return placement change is logically sound for leaks, but the blast radius for graceful reconnections requires careful verification during execution.
