# Cross-AI Plan Review — Phase 19.1 (Pass 6)

## Gemini Review

1. **Summary**
Pass 5's F-amendments successfully resolved most of the remaining administrative and reporting discrepancies. However, two critical logical errors survived into the final executable state of Plan 05. The `GoldenTraceWithActionsTest` 90% floor assertion remains mathematically impossible to pass because it compares successful game-logic executions against arbitrary queued actions, and the `ActionResolverDrainSemanticsTest` will fail due to capturing a mutable `ConcurrentHashMap` by reference before a concurrent overwrite. These must be addressed before execution.

2. **Strengths**
- The `markStalled` close-aware detach (D-07) and OOB 408 documentation cleanly resolves a complex deadlock while properly setting expectations for the client contract.
- The `ToxinPathGenerator` static refactor (Option A) elegantly removes mutable state without breaking the deterministic seed pipeline, ensuring golden trace stability.
- Anti-reflag annotations (F6) are a great touch to prevent circular AI review loops on deferred technical debt.

3. **Concerns**
- **HIGH: Plan 05 Task 05a 90% aggregate floor is mathematically unreachable.**
  - *Reference:* `19.1-05-PLAN.md` Task 05a Step 4 (E5.3 / C5.5 / F1 amendments).
  - *Detail:* The test loops over all live entities and assigns a verb based on `tick % 4`, meaning queued actions are ~25% M, ~25% E, ~25% R, and ~25% V. The `processedCountForVerb` increments *only on game-logic success* (e.g., `resolveMove()` returns true). Because the test bots are not staged with high energy or placed on nutrients, the vast majority of 'E' and 'R' actions will legitimately fail. Furthermore, 'V' actions will always fail (0% success) as there are no composites staged in the fixture. Therefore, the total processed count will naturally hover around 25-30% of `totalQueued`. Asserting `totalProcessed >= 0.9 * totalQueued` will unequivocally fail on every run.
- **HIGH: Plan 05 Task 05c DR-pin test assertion fails due to concurrent map mutation.**
  - *Reference:* `19.1-05-PLAN.md` Task 05c DR-pin test body.
  - *Detail:* The test seam observer calls `captured.set(snapshot);`, saving a reference to the mutable `ConcurrentHashMap`. The test then spawns a virtual thread that calls `queueAction(sessionId, newAction)`, which mutates that exact map. When the test later asserts `assertThat(captured.get()).containsEntry(sessionId, oldAction);` after the tick completes, it is reading the mutated map, which now contains `newAction`. The assertion will fail, throwing a false negative.

4. **Suggestions**
- **For Task 05a (90% floor):** Remove the 90% aggregate floor entirely. The test already asserts `processedCountForVerb(v) >= 1` for M, E, and R, which satisfies the sanity check that the parser isn't silently dropping everything. The golden trace digest comparison itself is the rigorous regression gate. If an aggregate floor is desired, set it to `> 0`.
- **For Task 05c (DR-pin test):** Change the observer capture to take a snapshot copy of the map's state at that exact moment. Use `captured.set(Map.copyOf(snapshot));` or `captured.set(new java.util.HashMap<>(snapshot));` so the assertion checks the pre-overwrite state as intended.

5. **Risk Assessment**
**HIGH** — The test logic flaws in Plan 05 are guaranteed to fail in CI, blocking the phase rollout despite the source-code fixes being correct.

## Claude Review

### 1. Summary

Most of pass-5 F-amendments hold. Found **one HIGH math bug in F1** (90% aggregate floor unreachable by construction), **two MED issues** (F3 reorder breaks Task 05f acceptance, E3.2 leaks stuck VT), and **one LOW** (E5.4 @DirtiesContext unnecessary). Other amendments verified consistent.

### 2. Strengths

- F2 set-equality fix correct: `[^)]+` regex + `Integer.MAX_VALUE` literal pin closes pass-4 dismissal gap.
- F4 restatement of E2.3 honest about cures flowing through pendingGrants; comparator totality argument intact via reduceInfection early-return.

- E3.1 markStalled signature fix (`3L` not `"stuck-VT-test"`) catches a real type error.
- Anti-reflag annotations (F6) well-placed and reference deferral rationale.

### 3. Concerns

#### HIGH — F1 aggregate 90% floor mathematically unreachable

Plan 05 Task 05a Step 4. Driver cycles `verb = switch (tick % 4) { 0→M, 1→E, 2→R, default→V }` — V is queued at ~25% of `totalQueued`. F1 amendment correctly excludes V from per-verb `>=1` floor (composite-only, fixture stages no composites → V never processes → `processedV.sum() == 0`). But aggregate gate is:

```
totalProcessed >= 0.9 * totalQueued
```

with V ≈ 25% of queued and 0% of processed:

```
max(totalProcessed) = processedM + processedE + processedR ≈ 0.75 * totalQueued
0.75 * totalQueued >= 0.9 * totalQueued   →  FAILS
```

Anti-reflag note claims "V's contribution (zero in this fixture, so it does not bias the gate)" — wrong. Zero numerator with ~25% denominator share guarantees ratio ≤ 75%. Gate cannot pass on first green run.

**Fix options:**
1. Restrict denominator to `{M, E, R}`-queued count (exclude V queues from `totalQueued`).
2. Remove V from driver's verb cycle until composite-aware fixture lands.
3. Lower aggregate floor to 70% (less safe, calibration drift).

(1) preferred — keeps denominator semantically meaningful (fraction of *processable* actions that processed). Update Task 05a Step 4 and the `must_haves.truths` baseline-commit-gate accordingly.

#### MED — F3 reorder breaks Task 05f acceptance criterion

F3 reorders execution to `05f → 05a → 05b → 05c → 05d → 05e`. But Task 05f acceptance still says:

> `./gradlew test --tests com.paralife.engine.GoldenTraceWithActionsTest` exits 0 **BOTH BEFORE AND AFTER** the hoist commit.

If 05f runs first per F3, `GoldenTraceWithActionsTest` does not exist yet (Task 05a creates it). The "before hoist commit" gate is impossible — no test class to invoke. Either:

- Drop the "before" gate entirely from Task 05f (only assert post-hoist green).
- Add explicit "this gate applies only when re-running 05f after 05a has landed" caveat.

Pick (a) — simpler. F3 already states the baseline encodes post-hoist behavior; pre-hoist test invocation is meaningless.

#### MED — E3.2 detach-timeout test leaks the stuck drain VT

Plan 03 Task 03a Step 5. Test fake's `sendMessage` blocks on `CountDownLatch never = new CountDownLatch(1)` and "ignores `Thread.interrupt()`". After `detachSession(String)` join-times-out, the drain VT is still parked on `never.await()` forever. No `@AfterEach` teardown counted-down. Each test run leaks one stuck VT into the shared JVM.

This conflicts with TD-22-A guidance (forkEvery=1 + leaked-thread alarm). Add explicit teardown:

```java
@AfterEach
void releaseStuckVT() {
    never.countDown();   // unblocks the drain VT, sendMessage throws IOException, loop exits
}
```

Or use a per-test latch field and count it down in finally. Plan should call this out.

#### LOW — E5.4 @DirtiesContext unnecessary

Plan 05 Task 05c. `@DirtiesContext(AFTER_EACH_TEST_METHOD)` rebuilds full Spring context between two tests. But both `overwriteMidDrainDefersToNextTick` and `noOverwriteDrainsCleanly` call `actionResolver.setDrainObserverForD20Pin(...)` as their first action — overrides any stale observer from prior method. The "stale observer fires" concern in E5.4's rationale is incorrect for this test pair.

Drop @DirtiesContext or downgrade to lighter `MockitoBean` reset. Not blocking; correctness-equivalent at higher cost.

### 4. Suggestions

- F1 fix: restrict denominator to `{M,E,R}` — see HIGH above.
- F3 fix: strike "BEFORE the hoist commit" from Task 05f acceptance — see MED above.
- E3.2 fix: add `@AfterEach` releasing the never-latch — see MED above.
- F4: confirm `tickBuffsAndInfections` (`:744`) cure-enqueue path also has the `(entity, initialTicks, position)` uniqueness invariant. F4 only argues from `reduceInfection.early-return`. If `tickBuffsAndInfections` lacks an analog guard, comparator totality is leakier than F4 claims. Worth a 5-min audit at execute time.

### 5. Risk Assessment

**MED** — F1 HIGH is a calibration bug, not a correctness gap; first green run catches it. F3 MED surfaces only when re-running 05f post-05a (rare). E3.2 MED accumulates over CI runs but doesn't break test correctness. Convergence is close; one more focused amendment pass (F-amend-2 or similar) closes these and ships.

## OpenCode Review

**HIGH concern — F2/C5.2 inconsistency makes set-equality verification impossible**

The F2 amendment broadens the `grep -oE` regex from `[0-9]+` to `[^)]+` so `@Order(TICK_ORDER)` and `@Order(Integer.MAX_VALUE)` from source participate in the `diff`. But the C5.2 CLAUDE.md table uses the **numeric values** `@Order(14)` and `@Order(25)` for EnvironmentEngine and EnvPostActionReconciler — not the symbolic `@Order(TICK_ORDER)` as annotated in source (`EnvironmentEngine.java:352`, `EnvPostActionReconciler.java:41`).

The set-equality `diff` at Plan 05 Task 05d acceptance can never exit with empty output: source side has `@Order(TICK_ORDER)`; CLAUDE.md side has `@Order(14)`/`@Order(25)`. These never match as strings. Additionally, the source grep captures comment-text `@Order(14)`/`@Order(25)`/`@Order(100)` from Javadoc (verified: adding noise to the source set), so even if TICK_ORDER were resolved, annotation-only comparisons would be unreliable.

Fix options: either (a) change the C5.2 CLAUDE.md table rows to `@Order(TICK_ORDER)` with a parenthetical like `(14)` / `(25)` in the description, and filter the source grep to annotations-only via `grep -vE '^\s*(//|\*)'`; or (b) drop the automated set-equality and replace it with manual row-by-row verification.

**MED concern — Plan 05 physical task ordering contradicts F3 reorder**

F3 amendment says "Plan 05 task ordering is 05f → 05a → 05b → 05c → 05d → 05e" with 05f (entitySnapshot hoist) executing before 05a (GoldenTraceWithActionsTest baseline pin). But the plan file lists tasks in document order 05a-05b-05c-05d-05e-05f. An automated executor processing tasks sequentially would run 05a before 05f, which is exactly the regression F3 was designed to prevent: the baseline would absorb post-hoist behavior, making `GoldenTraceWithActionsTest` vacuous as a hoist-regression gate. The plan's physical task list should be reordered to match the declared execution order.

**MED concern — Plan 03 Task 03a E3.2 test leaks a live VT**

The `detachTimeoutIncrementsCounter` test creates a fake `WebSocketSession` whose `sendMessage` blocks on an un-counted-down `CountDownLatch` *and* ignores `Thread.interrupt()`. After `detachSession(String)` fires the interrupt, `join(100ms)` times out, the counter increment is asserted, and the test method returns — but the drain VT remains alive and blocked. In a test suite, accumulated zombie VTs can prevent clean shutdown or cause ordering issues in later tests.

**LOW concern — Plan 03 Task 03a E3.2 test re-lookups meterRegistry after assertion but doesn't isolate the drain VT**

The E3.2 test uses `meterRegistry.counter(...)` which is a global registry. If another test increments the same counter in parallel, the `after - before == 1.0` assertion flakes. Adding `@DirtiesContext` at class level or counting before/after the detach call in a `synchronized` block would close the window.

- Anti-reflag annotations (F6 sites) correctly document deferred status with pass-5 triage dates
