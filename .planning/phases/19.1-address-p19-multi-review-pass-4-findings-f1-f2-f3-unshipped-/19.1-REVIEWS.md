# Cross-AI Plan Review — Phase 19.1

## Gemini Review

Here is the cross-AI review of the implementation plans for Phase 19.1.

### 1. Summary

The implementation plans for Phase 19.1 are exceptionally well-crafted, meticulous, and highly tactical. By relying strictly on established in-tree analogs and intentionally deferring larger refactors (like concurrent registration) to future phases, the plans successfully isolate the P19/P19.5 hardening work. The logical separation into parallelizable waves and the proactive inclusion of structural defenses—such as pinning the `drainActions` contract and creating the generic codec convention gate—demonstrate a mature, defensive approach to closing out reviewer findings while heavily guarding against future regressions.

### 2. Strengths

*   **Strict Analog Adherence:** Fixes are explicitly mapped to existing, proven patterns in the codebase (e.g., `remapEntity` for composite formations, copy-and-sort idioms for RNG), minimizing architectural drift and execution risk.
*   **Structural Defenses:** Pairing the F2 spot fix with the D-15 parameterized codec gate, and writing the DR-pin test to enforce the `drainActions` semantics, brilliantly converts isolated bug fixes into durable, CI-observable system invariants.
*   **Stateless Determinism Design:** Encouraging "Option A" (passing the seed per-call) for `ToxinPathGenerator` elegantly avoids advancing the global `spawnRng` state upon instantiation, preventing cascading verification failures in existing golden trace tests.
*   **Safe Wave Sequencing:** The dependency graph accurately prevents race conditions, ensuring foundational fixes (like determinism and payload parsing) land before the end-to-end golden trace baseline is pinned in Plan 05.
*   **Nuanced State Management:** The plans implicitly respect the protection of `STALLED` entities from `cleanupBot` (because `markStalled` strips the entity ID). This ensures the BL fix safely cleans up environmental state for true disconnects without accidentally wiping the state of backpressured entities currently in the grace window.

### 3. Concerns

*   **HIGH:** *Plan 02, Task 02a (F4 / D-04)*. Sorting `pendingGrants` solely by `entityId` may not produce a stable total order if multiple grants can be queued for the *same* entity in a single tick. If the sort is not a total order, the non-deterministic `ConcurrentHashMap` iteration order could still influence the relative sequence of `randomBuff()` consumption, leaving the determinism bug partially unresolved.
*   **MEDIUM:** *Plan 03, Task 03b (MS / D-07)*. After calling the close-aware `detachSession(session)`, the underlying socket is closed. The subsequent best-effort `sendOutOfBand` call is highly likely to throw an `IllegalStateException` or `IOException` (depending on Jetty/Spring WebSocket internals). If `sendOutOfBand` does not safely swallow these exceptions internally, it could bubble up and crash or abort the tick thread.
*   **LOW:** *Plan 05, Task 05a (GT / D-11)*. The `GoldenTraceWithActionsTest` plans to use deterministic but likely invalid targets for `E` (eat) and `R` (reproduce) actions (e.g., arbitrary IDs). While this successfully pins the parsing and validation paths, it will likely hit early validation rejections in `ActionResolver`, meaning the deep simulation execution paths of those verbs remain unexercised in the trace.

### 4. Suggestions

*   **Plan 02, Task 02a (D-04):** Expand the sort comparator to include a secondary deterministic key if `PendingGrant` contains one to ensure an absolute total order. For example: `snapshot.sort(Comparator.comparing(PendingGrant::entityId).thenComparing(PendingGrant::buffType))`.
*   **Plan 03, Task 03b (D-07):** Wrap the `sendOutOfBand` call inside `markStalled` in a broad `try-catch (Exception ignored)` block, or explicitly verify that `sendOutOfBand` already swallows socket-closed exceptions. This guarantees the tick loop is shielded from the best-effort courtesy frame failing.
*   **Plan 05, Task 05a (D-11):** Add a comment in the test acknowledging that deterministic verb generation may result in action-validation failures. If feasible without adding massive test complexity, attempt to use valid self-relative coordinates for targets to push the execution deeper into the resolver.

### 5. Risk Assessment

*   **Overall Risk Level:** **LOW**
*   **Justification:** The phase consists entirely of targeted, isolated bug fixes and test/doc enhancements. The reliance on established codebase patterns, combined with the safety net of the existing 166-test suite and the newly added invariants, drastically reduces the likelihood of regressions. The identified concerns are minor edge cases related to total-ordering and exception handling that can be trivially patched by the executor during implementation without altering the overarching architectural approach.

## 3. Concerns

### HIGH

- **C-01 [Plan 05 Task 05f / D-19] — ES hoist may change semantics, not just perf.** Plan claims "no behaviour change". This holds ONLY IF no consumer between the 4 call sites in `processInteractions` mutates the live entity set (kill, spawn, remap). If consumer N kills an entity and consumer N+1 currently calls `entitySnapshot()` again, consumer N+1 sees the kill. After the hoist, consumer N+1 sees the pre-kill snapshot. This is a real semantic shift inside a single tick. Plans 02/05 add a `GoldenTraceWithActionsTest` that would catch this — but D-19 does not require running it before/after as a gate. **Suggestion:** add an explicit acceptance criterion: `GoldenTraceWithActionsTest` digest unchanged across the D-19 commit.

- **C-02 [Plan 02 Task 02c / D-06] — Option A vs Option B branch is too high-stakes for an autonomous executor.** The plan correctly identifies that Option B advances `spawnRng` state and breaks golden-trace; it leaves Option A vs B as a "verify by reading the file" decision. If the executor mis-classifies and picks B without regenerating the baseline, Plan 02's whole-suite gate fails. Worse: if Option A is structurally infeasible at one of the two call sites (`:267` vs `:298`) but fine at the other, the executor could split — half stateful, half stateless. **Suggestion:** force Option A. If the call sites can't accept a per-call seed, defer D-06 entirely to Phase 20 with a TD entry. Don't ship a version that risks golden-trace re-baselining.

- **C-03 [Plan 01 Task 01d / D-15] — codec gate doesn't actually gate.** `@ValueSource(chars = {'E','A','H','T','M','R','L','N','S','D','B'})` is hardcoded. If a future contributor adds `'X'` to `Event.java` AND forgets to extend `validateEventCode`, the test still passes — because it doesn't test `'X'`. The intended gate behaviour ("future codec drift fails CI") requires the test to derive its codes from `Event.java` reflectively or via a static accessor (e.g., `Event.ALL_CODES`). **Suggestion:** either ship a `public static final char[] CODES` on `Event.java` and make the `@MethodSource` read from it, or accept the gate is regression-only (existing codes can't be silently broken) and rename the test to reflect that.

### MEDIUM

- **C-04 [Plan 01 Task 01b interfaces section] — `remapEntity` signature is mislabeled.** Plan 01 `<interfaces>` says `void remapEntity(String sessionId, String oldEntityId, Position pos)`. The PATTERNS.md analog at `:1255-1263` calls `botRegistry.remapEntity(sessionId, bondedPair.id(), pos)` where `bondedPair.id()` is the NEW id. Either the interface comment is wrong or the analog is. Executor will need to grep BotRegistry.java to disambiguate. **Suggestion:** read `BotRegistry.java:169-178` and pin the actual signature in the plan.

- **C-05 [Plan 03 Task 03b / D-07] — sendOutOfBand after close-aware detach.** After `outboundSender.detachSession(session)` closes the transport, `sendOutOfBand(session, ErrorFrame(408))` is called next. `sendOutOfBand` enters `synchronized(session)` and calls `session.sendMessage()` on a closed session — depending on Jetty 12 behaviour, this either silently fails, throws IOException (caught? rethrown?), or logs noise. Plan acknowledges this with "best-effort" but doesn't pin which path Jetty takes. If it throws an uncaught IOException, markStalled propagates an exception into the tick handler. **Suggestion:** wrap the OOB call in `try { ... } catch (IOException ignored) {}` (mirroring the existing close pattern), or remove the OOB attempt entirely since the close itself is the reconnect signal per the new doc.

- **C-06 [Plan 04 Task 04b / D-09] — clearInfectionOnDeath called on disconnect.** Method name is `clearInfectionOnDeath` but disconnect-without-death is a different lifecycle event. If the method has death-specific side effects (e.g., emitting a death event, applying compost, decrementing counters), calling it from `cleanupBot` is semantically wrong. **Suggestion:** verify the method is a pure infection-map remove. If it has side effects, add a sibling `clearInfectionOnDisconnect` or rename to `clearInfectionState`.

- **C-07 [Plan 04 Task 04b] — double-clear with DeathFinalizer.** If an entity dies and `cleanupBot` runs concurrently (or shortly after), both will call `buffRegistry.unregisterEntity`, `clearInfectionOnDeath`, `fleeingRemove`. Idempotency claimed but not asserted in the plan. If `clearInfectionOnDeath` increments a counter or emits a metric, double-call doubles the count. **Suggestion:** add an explicit acceptance criterion that all three calls are idempotent (or pin idempotency in the unit tests).

- **C-08 [Plan 03 Task 03c] — stuck-write simulation via FrameEmitListener.** The integration test uses a `FrameEmitListener` that latches inside `synchronized(session)`. This is NOT an actual stuck Jetty write — it's a stuck listener inside the monitor. The close-aware detach unblocks Jetty by closing the transport (causing `sendMessage` to throw IOException). With the listener as the blocker, the close on a different code path may release the listener via interrupt, but the test isn't validating the production unblock path (Jetty IOException → drain VT exit). **Suggestion:** prefer a slow-reading client (BlockingWebSocketClient on the read side) OR document that the FrameEmitListener latch is an *upper-bound model* of the stuck-write scenario, not a precise reproduction.

- **C-09 [Plan 05 Task 05c / DR-pin] — test seams undefined.** Test references `simulateOverwriteAfterDrainSnapshot()` and `peekPendingAction()` which don't exist on `ActionResolver`. Plan says "may need to be added as package-private helpers" — adding production test seams to pin a contract is a code change that could fail review on its own merits. **Suggestion:** commit upfront to one approach: either (a) add the seams with explicit Javadoc "Phase 19.1 D-20 test seam — pins drainActions semantics", or (b) construct the test purely against `queueAction` + `drainActions` public surface using monitor-based interleaving on a same-thread basis. Option (b) is cleaner.

- **C-10 [Plan 02 Task 02b] — inner shuffle determinism unverified.** Plan claims "the shuffle inside is fine (consumes seeded compositeRng in a stable order)". Not asserted. If `composite.getMembers()` returns a `Set` or CHM-backed collection, the `memberIds` list passed to `Collections.shuffle` has non-deterministic source order; the shuffle then has stable RNG inputs but unstable outputs. **Suggestion:** read `processCompositeEnergy` and verify `memberIds` is constructed in a deterministic order (sorted, list-of-members preserved at composite-creation time, etc.). If not, add a sort there too.

### **HIGH-01: D-04/D-05 sort keys may not guarantee byte-exact order**

**Plan**: Tasks 02a/02b sort by `entityId` (String) and `compositeId` (String).
**Issue**: String compare is locale-sensitive and JVM-version-dependent unless explicitly using `String.CASE_INSENSITIVE_ORDER` or a stable comparator. If entityIds contain mixed-case or Unicode, results may vary across runs/platforms.
**Evidence**: PATTERNS.md §D-04 says "String compare is sufficient" without specifying comparator.
**Impact**: Determinism tests may flake on CI vs local.
**Fix**: Use `Comparator.comparing(T::stableKey, Comparator.naturalOrder())` to ensure stable lexicographic order.

### **HIGH-02: D-07 tick-thread bound test is timing-flaky**

**Plan**: Task 03c asserts `maxTickMs < 50` under stuck-VT scenario.
**Issue**: The bound is arbitrary and environment-dependent. CI VMs under load may exceed 50ms even with correct behavior. The test lacks baseline calibration.
**Evidence**: PATTERNS.md suggests raising bound to `baseline * 5` if needed, but doesn't define how to measure baseline.
**Impact**: Flaky CI failures masking real regressions.
**Fix**: Run a short pre-calibration loop to measure `lastTickWorkMs` under normal conditions, then set bound to `calibratedMax * 10`. Document the calibration value in test output.

### **MEDIUM-03: D-09 double-close risk in BuffRegistry**

**Plan**: Task 04b adds `buffRegistry.unregisterEntity` in `cleanupBot`, but DeathFinalizer may also call it via `finalizeParticleDeath:109-122`.
**Issue**: If disconnect races with natural death, both paths may execute. `unregisterEntity` is documented as idempotent, but the registry's internal state (e.g., counter metrics) may double-decrement.
**Evidence**: PATTERNS §D-09 copies verbatim from DeathFinalizer without checking for atomicity.
**Impact**: Metric drift, not functional bug.
**Fix**: Add a comment in `DeathFinalizer` and `cleanupBot` noting the idempotency contract and that metrics are best-effort under race.

### **MEDIUM-04: D-11 action frame construction is underspecified**

**Plan**: Task 05a's `driveScenario` constructs ActionFrames with "deterministic args" but doesn't specify how.
**Issue**: The plan says "Verify exact ActionFrame ctor by reading Frame.java" but provides no concrete pattern. If Frame.ActionFrame requires live grid references or neighbour entity IDs, deterministic construction may be complex.
**Evidence**: PATTERNS.md §D-11 leaves Frame construction as `/* construct ActionFrame with verb, using deterministic args */`.
**Impact**: Implementer may pick unstable arguments (e.g., HashMap iteration order) defeating determinism.
**Fix**: Provide a concrete example: use `(tick + entityId.hashCode()) % 4` for direction, `neighbourId = grid.getAdjacencies(pos).get(0)` with snapshot-stable getter.

### **MEDIUM-05: D-06 ToxinPathGenerator seed plumbing may advance spawnRng**

**Plan**: Task 02c Option A plumbs the :404 seed by changing `generatePath` signature to accept `long seed`.
**Issue**: If any *other* caller of `generatePath` exists (e.g., in tests, or future code), it must also provide a seed. The plan doesn't audit call sites.
**Evidence**: grep shows only `:267` and `:298` construction sites, but `generatePath` may have other callers not shown in CONTEXT.md.
**Impact**: Forgetting to plumb seed at a new call site re-introduces non-determinism silently.
**Fix**: Add `@Deprecated` to the no-arg `generatePath()` and leave a comment pointing to the seeded overload.
